# Bruce 全仓对抗性审查报告

> **审查日期**: 2026-10-16 ｜ **审查范围**: 主干 `main` @ `fa499f2`
> **审查方式**: 架构基线对照 + 对抗性缺陷复核 + 门禁实跑（非声明核对）
> **结论**: 架构分层**未被敏捷修复破坏**（清理干净、依赖方向正确），但存在 **3 项高危健壮性缺陷** 与 **4 类架构债**（补丁叠加、重复实现、跨端漂移、双写状态）。

## 0. 结论速览

| 维度 | 评价 | 关键依据 |
|---|---|---|
| 分层架构完整性 | **良好** | provider 零文件 I/O、domain 零 I/O、local 不做定价；C038 脚手架由 C039 完整回收（全仓零残留） |
| 敏捷修复是否破坏架构 | **未破坏，但有职责渗漏** | application 层出现 codex/claude/grok 专属分支；bridge 协议层内嵌 provider 校验 |
| 代码健壮性 | **存在 3 项高危** | 凭据静默全损路径、生产 panic 路径、面板隐藏态动画未门控 |
| 开发规范性 | **良好，局部失真** | Rust 132 项测试全绿、clippy/fmt 零告警；但 design/00–04 停留在 2026-09-23、技术债池形同空池 |
| 测试体系 | **强** | 9+ Harness + 双端 fixture 对拍 + 真机 CI 三作业；缓存/窗口类缺陷有红绿用例锁定 |

**健康度评分：7/10。** 扣分不在架构设计，而在「修复密度高于结构收敛速度」——同类问题被反复用局部补丁解决，缺少一次性收敛。

## 1. 整体架构（实测还原）

### 1.1 分层与规模

```
apps/macos   138 Swift 文件 / 52,356 行   SwiftUI 菜单栏常驻（BruceApp · BruceAppCore · BruceOnboardingCore · BruceGlassSurfaceCore）
apps/win      24 Rust 文件 /  9,311 行   Tauri 2 + 原生 JS 前端（src-tauri · viewmodel crate）
apps/widget    1 文件      /  1,000 行   单文件 Web Widget
core/collector 22 Rust 文件 / 19,058 行   9 crate workspace（domain·local·aggregate·runtime·provider·credential·application·bridge·bin）
```

**依赖方向（实测）**：`domain`（零依赖领域层）← `local`/`aggregate`/`provider`/`credential` ← `application` ← `bin`。`provider` 全文件无 `std::fs` 调用，`domain` 仅依赖 chrono/serde——**设计文档约定与实际实现一致**。

### 1.2 职责边界（正面确认）

- **额度取数唯一归属 Rust**：Swift 侧 `URLSession/URLRequest` 出现 0 次（`SubscriptionService.swift` 无出站请求），11 家 provider 的额度出站全部在 `collector-provider`。`ProviderConnectionVerifier.swift:230` 甚至有注释显式声明「真实额度查询由 collector 完成, 此处不发网络请求」——**跨语言职责边界有文档化自觉**。
- **凭据单向注入**：凭据经 Bridge stdin JSON 传入 Rust，stdout 仅返回脱敏指标；`bridge_process.rs` 有进程级断言 stderr 必须为空。
- **SQLite 全只读**：`sqlite_cache.rs:211`、`sources.rs:2660`、`SQLiteSchemaProbe.swift:71` 均强制 `READ_ONLY`。

### 1.3 跨端一致性机制（项目独有亮点）

`tests/fixtures/geometry-parity/cases.json`（50 例：5 档分辨率/DPI × 4 方向 × 托盘状态）由 Rust 与 Node **双侧读取对拍**，进 CI。这是本仓最值得保留的工程资产——在没有 Windows 真机的条件下把「Demo 与实现漂移」变成可自动发现的问题。

## 2. 对抗性审查：敏捷修复是否破坏架构

### 2.1 正面发现：C038→C039 的脚手架回收是真清理

C038（2026-10-16）引入 `LedgerCache` 端口 + `FileLedgerCache` + `query_with_cache` 默认实现，同日 C039 因改用服务端权威端点将其**整体删除**。实测核验：

```bash
grep -rn "LedgerCache\|query_with_cache\|ledger_cache" --include='*.rs' --include='*.swift' .
# → 仅 docs/ 与 CHANGELOG 的历史备案命中，代码零残留
```

`git show b16a511` 显示删除 `collector-local/src/ledger_cache.rs`（−120 行）、runtime 端口（−23 行）、provider 台账代码（−1076 行）。**「造了又拆」没有留下幽灵抽象**，这是敏捷开发中最容易失控的一环，此处守住了。

### 2.2 缺陷一：provider 专属逻辑上浮到编排层 [中]

抽象设计意图是「新增 provider 只改 provider crate」，实际需要改 3 个 crate：

| 位置 | 内容 | 证据 |
|---|---|---|
| `application/execution.rs:250-268` | `codex_challenge()` 内判 `plan.service.app == "codex"` | 编排层硬编码 provider 名 |
| `application/execution.rs:270-303` | `finalize_codex_service()` 注入 `freshness`/`failureKind` | 仅 codex 有这两字段 |
| `application/execution.rs:333-337` | `resolve_credential()` 硬编码 `"claude"`/`"grok"` 返回 `CREDENTIAL_MISSING` | 凭据解析特例 |
| `application/lib.rs:106-113` | `codexQuotaRetryOnly` 特例短路整个采集流程 | 编排分支 |
| `bridge/lib.rs:333-458` | `validate_codex_request()` 协议层校验 codex 语义 | 协议层渗漏 |

**判断**：这不是「破坏架构」，而是**抽象没跟上业务演进**——codex 的多账号挑战/重试语义确实特殊，但当前以「编排层 if 分支」承接，导致抽象收益递减。建议下沉为 provider 层标准化输出（如 `ProviderOutcome { freshness, failure_kind, challenges }`）。

### 2.3 缺陷二：双份 provider 映射表，无编译期约束 [中]

```
collector-provider/lib.rs:19-80   CATALOG_SPECS   → (provider, prefix, app)
collector-application/account.rs:15-26  ACCOUNT_FIELDS → (app, credentialField)
collector-application/account.rs:34-48  account_prefix → app → prefix   ← 与 CATALOG_SPECS 逐字重复
```

三处前缀字符串（`"opencode_go_"`、`"kimi_coding_"` …）必须手工保持一致，**无任何编译期或测试期约束**。新增 provider 时漏改一处 → 静默取不到凭据。

### 2.4 缺陷三：凭据迁移逻辑跨语言两套实现 [中]

`credentials.rs`（Windows，555 行 lifecycle）与 `CodexCredentialStore.swift`（macOS，814 行，约 55% 是迁移/校验机器）各自实现了「旧格式 → v2 账号库」迁移。两端 schema 独立演进，无对拍 fixture 覆盖迁移路径。

### 2.5 归档判断

| 卡号 | 类型 | 是否留下结构债 |
|---|---|---|
| C038→C039 | 造脚手架→拆脚手架 | **否**，清理干净 |
| C025→C037 | Cline 窗口模型两轮修正 | **已解决**，C039 改为直读端点后「客户端建模」整套消失，并写入 design/02 红线 |
| C027–C036 | Windows 逐功能对标（11 张卡） | **是**，Swift/Rust 双端同构逻辑无共享源，靠 fixture 对拍约束 |
| C040/C041 | 缓存身份门禁 / 截断降级 | **部分**，见 §3.2 遗留文案与未收敛的 panic 路径 |

## 3. 健壮性审查（高危项，均经源码复核）

### 3.1 【高】凭据文件损坏 → 全部凭据静默清空

**位置**：`apps/macos/Sources/BruceOnboardingCore/OnboardingConfiguration.swift:717-724`（读）+ `:634-643`（写）

```swift
private func loadPayloadLocked() -> Payload {
    guard fileManager.fileExists(atPath: fileURL.path),
          let data = try? Data(contentsOf: fileURL),
          let payload = try? JSONDecoder().decode(Payload.self, from: data) else {
        return Payload()          // ← 任何读/解码失败 → 静默返回空 payload
    }
    return payload
}

public func saveCredential(_ value: String, forAccount account: String, ...) throws {
    var payload = loadPayloadLocked()      // ← 损坏时为 {}
    payload.credentials[account] = value
    try writePayloadLocked(payload)        // ← 整体覆盖写：其余全部凭据被抹除
}
```

**影响链**：credentials.json 出现任何损坏（断电截断、手工编辑语法错、磁盘满）→ UI 显示「未配置」而非报错 → 用户重新保存任一凭据 → **其余全部凭据被永久清除**，无备份、无回滚。

**同仓对照**（说明这是实现疏漏而非设计取舍）：
- `AtomicJSONStore.swift:141-200` 具备完整套件：创建即 0600 → `synchronize()` fsync → **重读校验** → `replaceItemAt` → 复位权限 → `backup/rollback`；
- `CodexCredentialStoreTests.swift:431` 有专门用例断言损坏 JSON 返回 `.corruptedJSON` **且不删除旧键**。

`ProtectedFileCredentialStore` 是唯一直接持有全部 API Key 的存储，却用了全套件里最弱的一档实现。

**权限实况（已核实，非推测）**：本机 `~/Library/Application Support/Bruce/credentials.json` 实测 `-rw-------`（0600 生效，`replaceItemAt` 会保留临时文件属性）。permission 结论：**当前安全**；但 `:742`/`:749` 的 `try? setAttributes` 失败被吞，属脆弱实现，建议随上面一并收敛。

### 3.2 【高】生产路径 panic 可使采集进程无 envelope 硬崩

**位置 A**：`core/collector/crates/collector-local/src/sqlite_cache.rs:463-465`

```rust
contribution: CompactContribution::from_domain(contribution, &config.window)
    .expect("usage contribution must match its collection window"),
```

`from_domain` 在「某天的索引不在当前 window.day_list 中」时返回 `None`（`collector-local/src/lib.rs:514-526`）——**这正是 C040 认定「窗口身份错位在现实中会发生」的那类条件**。C040 在增量追加前加了 `cache_identity_matches` 门禁（正确），但把同一类不匹配留成了进程级 panic。

**位置 B**：`application/lib.rs:119-120`、`:392` 的 `join().expect(...)`——worker 线程 panic 会升级为主线程 panic。

**放大器**：`bin/Bruce-collector/src/main.rs` 全文无 `catch_unwind`，panic 时 stdout 无任何 JSON envelope，Swift 侧仅见非零退出码（`CollectorRunner.swift:571`），用户得到笼统失败而无法区分「哪个源坏了」。

### 3.3 【高】面板隐藏态仍有未门控的持续动画/定时器

项目已建立 `DashboardPanelAnimationPolicy`（hero / heatmap 门控）并修复过「隐藏面板动画不暂停致 40% CPU」事故，但**只覆盖了 2 条路径**，实测仍有 3 处遗漏：

| 位置 | 问题 | 说明 |
|---|---|---|
| `Views/SubscriptionCard.swift:332-337` | `ProviderRefreshButton` 的 `ProgressView()` 无门控 | `MenuBarViews.swift:367-379` 调 `SubscriptionCard` 时**根本没传 `panelVisible`**（对比同文件 `UsageHeroCard` 传了 `model.dashboardPanelVisible`）。定向刷新最长 90s，其间面板若 orderOut，该 spinner 在常驻视图树里持续动画 |
| `MenuBarViews.swift:534` | `SuppressorView.watchdog` 0.3s 重复 Timer | 只在 `viewDidMoveToWindow(nil)` 停止（`MenuBarStatusItemController.swift:536` 仅 `orderOut`）——**首次打开面板后该 Timer 终身 0.3s 一跳** |
| `Views/HourlyLineCard.swift:238-240` | `.task(id:)` → `growColumns()` 含 `Task.sleep` + `withAnimation` | 按日期轴变化重跑，未过 `panelVisible`；每次 artifact 刷新（30 分钟）可能触发一次约 0.4s 动画批 |

第 1 条是 `panel-longlived-view-task-gotcha`（已知坑 b）的**最后残留**，且恰好落在「刷新最长 90s」这个最容易观测到的窗口内。

### 3.4 【中】静默吞错使故障不可见

| 位置 | 后果 |
|---|---|
| `application/lib.rs:729` `let _ = accumulator.merge_delta(...)` | 合并失败被吞，`agent.status` 仍为 ok，用量静默丢失（同文件 `aggregation.rs:48-56` 同类失败会产诊断——**口径不一致**） |
| `application/lib.rs:614-618` `Err(SourceScanError::Io(_)) => Ok((SourceScan::empty(...), metric))` | 次要源 I/O 错误无任何诊断 |
| `sources.rs:1695` `let _ = builder.merge_contribution(&cached.aggregate)` | Codex 树缓存解码异常静默 |
| `ProviderAccountStore.swift:260-261,288` `try? decode ?? ProviderAccountIndex()` | 索引解码失败静默重置为空，随后 `saveIndex` 覆盖 → Keychain 遗留记录成孤儿 |

### 3.5 【中】目录递归防护不一致（symlink 环）

- **有防护**：`sources.rs:344-353` `walk_jsonl_tree` 带 `MAX_DIRECTORY_SCAN_DEPTH=16` + `visited_dirs` 集合，并有专门测试 `sources.rs:5207-5230`（防 symlink 环）。
- **无防护**：`jsonl_cache.rs:227-277` `visit_tree` 与 `sources.rs:488-570` `collect_codex_files` 递归时**既无深度上限也无 visited 集合**。

同一仓库里同一个问题存在「已验证的解法」与「未防护的新实现」两套代码——属典型的「新写缓存路径时没复用旧护栏」。

### 3.6 【低】C041 遗留文案与常量不一致

`sources.rs:35` `MAX_SOURCE_ROWS = 30_000`，但 `sources.rs:2919` 的 opencode 截断诊断仍写 `"仅保留 opencode 最新 10000 条候选消息"`。C041 把上限从 1 万改 3 万时漏改该文案，用户可见文案与实际行为不符。
