## 1. 简介 (Introduction)

本方案定义 `Bruce` 的核心数据引擎 —— **Core Collector**。
Core Collector 独立运行于 `core/collector/`，由纯 Rust 打造，作为高吞吐、零内存泄漏的守护采集进程。

- **业务动因**：现代开发者通常在本机多 Agent 并行开发（如使用 Claude Code 自动化重构、Codex 审查代码、Kimi Code 分析仓库、OpenCode 执行终端操作等）。每个 Agent 拥有独立的会话目录、专有的日志格式（JSONL、SQLite、增量转储）及不同的模型标记。开发者迫切需要一个统一、轻量、近实时的引擎，快速扫描本地日志并折算为统一的 Token 与美元费用指标。
- **系统定位**：作为底层数据生产引擎，向下只读扫描用户家目录下的 Agent 会话日志与云端额度接口，向上通过标准 IPC（JSON over stdio）为应用层（macOS App / Web Widget）提供强类型标准工件（Artifact）。

## 2. 目标与非目标 (Goals & Non-Goals)

### 2.1 目标 (Goals)
1. **多源异构会话即时扫描**：原生支持 Claude Code, Codex, Kimi Code, OpenCode, CodeBuddy, Grok, Pi, ZCode, DeepSeek Harness (dsh) 等 9+ 主流 Agent 的日志解析（含 zstd 压缩 JSONL 事件流）；
2. **增量指纹与零冗余 I/O**：基于 `64KB Segment Fingerprint` + `mtime/size` 双重缓存策略，冷启动后二次扫描延迟低于 50ms；
3. **多模型精密计费**：内置主流大模型基准价卡（输入、输出、Cache Read 单价与缓存写入 TTL 倍率，唯一事实源 `pricing-catalog.json`，C108），支持模型别名归一化与用户自定义覆盖（Overrides）；
4. **强健的系统安全性**：对符号链接提供防环保护（Cycle Prevention），读取外部应用 SQLite 时强制 `mode=ro` 只读连接，绝不破坏宿主会话。

### 2.2 非目标 (Non-Goals)
1. **不拦截或代理模型网络流量**：不充当本地反向代理或网关，纯旁路离线审计；
2. **不修改或清理第三方 Agent 会话文件**：严禁向扫描目录执行写入、删除或格式化操作；
3. **不提供跨机器数据同步服务**：所有采集和聚合逻辑均在单机闭环。

## 3. 需求分析 (Requirements)

### 3.1 功能需求清单
- **FR-1 多源扫描**：自动探测本机 `~/.claude/`、`~/.codex/`、`~/.kimi/`、`~/.dsh/` 等标准路径，兼容单文件 JSONL、zstd 压缩 JSONL 事件流、分片目录与 SQLite 状态库；
- **FR-2 时间窗口切片**：支持今天（Today）、过去7天（7d）、过去30天（30d）与全量（All-time）四维时间窗口聚合；
- **FR-3 维度多维交叉**：支持 `Agent × Model × Month`、`Agent × Project` 等多维聚合，生成模型分布占比与趋势数据；
- **FR-4 成本换算**：按各模型具体输入 Token、输出 Token、缓存读取 Token（Prompt Cache Read）分别乘以单价并折算为 `costUsd`。

### 3.2 非功能需求 (NFR)
- **性能指标**：冷启动扫描 10,000+ 条会话日志总耗时 < 1.5 秒；增量缓存命中时总耗时 < 80 毫秒；
- **内存开销**：单次完整采集峰值内存占用 < 35 MB，任务完成后瞬时释放；
- **架构兼容**：支持 Universal 2 二进制（`arm64-apple-darwin` 与 `x86_64-apple-darwin`）。

## 5. 总体设计 (High-Level Architecture)

### 5.1 Rust Collector 内部 Crates 结构

```text
core/collector/
├── crates/
│   ├── collector-domain/       # 纯领域模型: Session, Turn, TokenBucket, PricingTable
│   ├── collector-local/        # 本地扫描引擎: 10 个 Agent 适配器、增量缓存、防环
│   ├── collector-provider/     # 云端出站适配器: HTTP 客户端、Provider 额度解析
│   ├── collector-credential/   # 凭据抽象与挑战校验
│   ├── collector-aggregate/    # 增量累加器 UsageAccumulator、多维统计
│   ├── collector-history/      # 派生数值历史台账: SQLite schema、单调合并、窗口投影 (T26, §7.3)
│   ├── collector-application/  # 编排调度、RunContext、多源任务并发分发
│   ├── collector-policy/       # 跨端共享的每轮刷新策略: 额度门禁与回填 (design/08, T13)
│   ├── collector-policy-ffi/   # 共享策略的 C ABI 静态库 libbruce_policy.a, mac 进程内链接 (T16)
│   └── collector-bridge/       # CLI 入口与 IPC 协议处理
└── schemas/                    # JSON 契约定义 (request-v1, response-v1, agent-usage-v1, policy-request-v1, policy-response-v1)
```

#### 现行设计规则

##### 1. 内置基准价卡 (`PricingTable`)
系统内置覆盖主流厂商的基准定价（单位：美元 / 百万 Token）。**唯一事实源为 `collector-domain/pricing-catalog.json`（C108）**：`PricingTable::new` 加载全部行，Windows / mac 设置页的展示目录均由同一文件派生（规则见 design/04「价卡单一事实源」），下表为主要行摘录，逐条以 JSON 为准：

| 模型分类 | 模型标识 (Key) | Input / 1M | Output / 1M | Cache Read / 1M |
|---|---|---|---|---|

##### 2. 费用核算计算式
对于任意用量切片，总费用计算严格遵循以下纯函数公式：
$\text{Cost} = \frac{\text{input} \times P_{\text{in}} + \text{output} \times P_{\text{out}} + \text{cacheRead} \times P_{\text{cache}} + (\text{write}_{5m} \times m_{5m} + \text{write}_{1h} \times m_{1h}) \times P_{\text{in}}}{1,000,000}$
- **缓存写入按 TTL 拆分（C107）**：`write_1h` 取 Claude Code 日志 `usage.cache_creation.ephemeral_1h_input_tokens`（贯穿 `TokenBucket.cache_creation_1h`，上限为 `cache_creation`），其余缓存写入计为 `write_5m`；未区分 TTL 的来源全部计为 5 分钟写入。倍率 `m_5m` / `m_1h` 由价卡行声明（`cache_write_multiplier` / `cache_write_1h_multiplier`），Anthropic 行为 1.25 / 2.0，未声明时 `m_5m = 1.0`、`m_1h = m_5m`（即按输入单价计，与 C107 前一致）；
- 当模型命中用户在设置中配置的自定义覆盖项（`ModelPricingOverride`）时，优先采用覆盖单价；缓存写入倍率沿用内置行（覆盖输入单价时写入成本随之等比变化）；
- 未匹配到任何价卡行（含覆盖项）的模型**不估算费用**：对应桶 `costUsd` 为 `null`，工作台计入「未定价 tokens」。

##### 3. 增量缓存机制与文件防环
- **分段哈希**：扫描器仅对会话文件头部及末尾 64KB 执行 SHA-256 计算，避免对数百兆历史日志全量重哈希；
- **源级缓存 (C021 起)**：JSONL 与 SQLite 源在未变更（按身份/指纹判定）时直接复用上次解析结果（`jsonl_cache.rs` / `sqlite_cache.rs`），避免重复解析整棵源树；缓存启用与失效路径需与冷扫结果逐字段一致（`cached_*_sources_match_cold_and_warm_results` 系列用例锁定）；SQLite 缓存签名含**库文件头 change counter**（偏移 24 大端 u32）与（Windows）**创建时间身份**，使「替换 vs 追加」判定不依赖文件时间戳粒度（C022：Windows 时间戳粒度约 15ms，仅凭 size/mtime 会把替换误判为追加并静默返回陈旧用量）；
- **增量追加身份红线 (C040)**：SQLite 游标增量追加必须以**缓存身份全匹配**（窗口长度/时区/今日，`cache_identity_matches`）为前置——身份错位（如以不同 `days`/时区参数直跑 collector）时旧条目的天索引在新窗口 `day_list` 下会错位或越界，此时严禁增量合并，必须整体回退全量重建；base 解码失败（`to_domain` = None）同样回退重建，**严禁以空 base 合并后推进游标**（该路径曾把历史整体清空且无自愈，回归用例 `zcode_sqlite_cache_window_mismatch_rebuilds_instead_of_empty_append` 锁定）；
- **聚合格式版本红线 (C072)**：SQLite 缓存条目身份必须包含**聚合格式版本**（`aggregation_version`，与 JSONL 缓存条目同一防线）——任何影响缓存贡献形状的聚合演进（如 C070 的 `day_models`/`hour_models` 明细桶）都必须同步提升 `AGGREGATION_VERSION`，令全部旧条目身份失配回退全量重建。C070 曾只以 serde 可缺省字段兼容旧条目而漏设此门禁：升级后无明细的 v2 条目被当合法 base 增量追加，历史逐日/逐小时模型明细永久缺失而月明细幸存（月/日视图口径分裂），回归用例 `zcode_sqlite_cache_aggregation_version_mismatch_rebuilds_detail` 锁定；
- **历史台账与全量读取 (T26，取代 C041 行数截断)**：SQLite 源不得设行数上限——ZCode/OpenCode 全量与增量读取一律按 rowid/时间游标流式逐行聚合（内存 O(1)、逐行取消检查），`MAX_SOURCE_ROWS` / `SourceScan.capped` / `SqliteReadResult.capped` / `LOCAL_SOURCE_ROWS_CAPPED` 均已删除。全部 agent 的派生数值（日 / 日×模型 / 月×模型 / 今日小时与工程）写入 collector 自有 `usage-history-v1.sqlite` 台账（单调合并、来源消失不抹历史），artifact 从台账投影；来源消失但台账有量时 `status=history`。台账失败以信息级诊断 `LOCAL_HISTORY_STORE_UNAVAILABLE` 降级为「仅扫描贡献」，**不参与 envelope Partial 判定**；`LOCAL_SOURCE_SCHEMA_INCOMPATIBLE` 仍只用于真实 schema/读取故障（详见 §7.3；说明性信息走 `LOCAL_SOURCE_NOTICE`，见「来源诊断分级 (C198)」）；
- **取消语义 (C021 起)**：本地扫描在源循环与目录遍历层均检查 `CancellationToken`，取消时停止扫描并以 `LOCAL_SOURCE_CANCELLED` 拒绝发布半成品 artifact（发布前设终态栅栏）；单 root 的 I/O 错误按 `io_errors` 计数并保留已得贡献，不整次失败；
- **防环保护**：维护 `visited_inodes: HashSet<(u64, u64)>`（针对 Unix 文件系统 `(dev, ino)`）与目录 canonical 路径集合，当检测到重复节点或深度超过 16 层（`MAX_DIRECTORY_SCAN_DEPTH`）时立即切断，防止符号链接循环导致的死循环或栈溢出。
- **生产路径不得以 panic 表达数据不匹配 (C043)**：缓存条目构造中 `from_domain` 返回 None（某天不在当前窗口 `day_list`）一律「放弃写该缓存条目 + 计 `cache_corruptions`」，严禁 `expect`；worker 线程失败（local/quota/aggregation）一律降级为 `COLLECTOR_WORKER_PANICKED` 诊断而非 `join().expect`；采集入口 `run_bytes_panic_safe` 以 `catch_unwind` 兜底输出 `BRIDGE_INTERNAL_PANIC` error envelope，保证 stdout 恒有可解释 JSON（此前 panic 会让宿主只看到非零退出码）；
- **目录递归双护栏 (C045)**：全部会话目录遍历（未缓存 walker、JSONL 缓存适配器、Codex 文件收集）共用 `MAX_DIRECTORY_SCAN_DEPTH` 与 canonical 已访问集合双重护栏，任一实现缺一即视为缺陷（用例 `jsonl_cache_adapter_survives_symlink_cycle` 以 `files_visited` 计数锁定护栏有效性）；
- **降级必须可见 (C046)**：聚合合并失败 → agent 降级 `partial` 且 note 说明数据不完整（不再静默丢用量）；次要源 I/O 错误 → 信息级诊断 `LOCAL_SOURCE_IO_DEGRADED`（区分「源不存在」与「读取失败」）；Codex 树缓存解码异常 → 计 `cache_corruptions` 并以信息级 `LOCAL_SOURCE_NOTICE` 说明（C198 前误走故障通道把 Codex 置 `error`）；
- **来源诊断分级 (C198)**：来源扫描结果分两个通道——`SourceScan.diagnostic` 只承载**真实故障**（SQLite 库不可读 / schema 不兼容 / 查询失败），输出 `LOCAL_SOURCE_SCHEMA_INCOMPATIBLE`、agent 置 `error`、envelope `Partial`；`SourceScan.notice` 承载**说明**（Codex 缓存损坏已整体重建、会话副本分叉已按单次响应合并（C190），以及后续卡片的截断 / 解析失败计数等用量完整或少计可解释的信息），输出信息级 `LOCAL_SOURCE_NOTICE`（stage 为来源 id，与 `LOCAL_HISTORY_STORE_UNAVAILABLE` 同样**不参与 envelope Partial 判定**），agent 状态保持扫描结果（`ok` / `history` 等，双端不生成 `.agentIssue`），说明以「原 note (说明)」形式附在 `agent.note` 后；故障与说明并存时 note 只显示故障。新增说明一律走 `notice`，严禁再经 `diagnostic` 输出非故障信息（会让来源每轮显示 error）；
- **缓存写盘与解析热路径 (C110)**：缓存条目一律**先序列化到内存再单次 `write_all`**，严禁 `serde_json::to_writer` 直写未缓冲的 `File`（每个 JSON 记号一次 `write` 系统调用，曾占 Claude 冷扫 0.6 s 内核态）；会话文件以 64 KiB `BufReader` 读取并复用行缓冲；JSONL / Codex 解析前先做字节级预筛（Claude / Pi `"assistant"`、CodeBuddy `"assistant"`/`"function_call"`、Codex `turn_context`/`token_count`、Kimi Work `usage.record`、Grok `"user"`/`"assistant"`、dsh `"usage"`/`"cwd"`），不含判定字面量的行计 `ignored_lines` 而不构建 JSON DOM —— 预筛子串必须是适配器产出用量的必要条件；
- **本机源并行扫描 (C110 / C116 / C189)**：10 个本机源（Kimi Code CLI 居首，C116 起不再是独立主源）交给 `RuntimeLimits.local_workers`（默认 4）大小的工作池，每个任务持一个本机扫描许可；结果按固定源序合并，诊断与 `source_metrics` 顺序不变（`source_metrics_follow_the_stable_local_source_order` 锁定）；单个工作线程 panic 降级为该源空结果 + `COLLECTOR_WORKER_PANICKED`；
- **Orca 内置 Codex 计入 Codex (C119)**：Orca 内置 Codex 的会话目录（`codex-runtime-home/home/sessions` 与 `codex-accounts/*/home/sessions`）与 Codex CLI 是同一种 rollout，必须在**同一次** Codex 扫描里跨根去重（硬链接 / 内容相同的副本零解析跳过，其余同名副本按单次响应去重取并集，见下条）并全部计入 `codex` 行；artifact 不设 Orca 行（维护者决定，2026-10-26）。严禁把 Orca 目录拆成独立源各扫一遍（会把同一会话计两次）。
- **同名副本按单次响应取并集 (C190)**：rollout 文件名含会话 UUID，同名即同一会话；多个根中的同名副本（Orca 旧前缀副本、分叉副本）**不得整份择一**（分叉部分会静默少计），也**不得各自全额计入**（共享前缀重复计入，且 T26 台账单调取大，多计永久落库）。正确口径：每份非相同副本逐份解析（各自按文件缓存），每条观测带单次响应去重键——Codex 0.164+ 的 `token_usage_record` 紧挨 token_count 写入，用量相同时取其全局唯一 `response_id`（`r:<id>`），旧版 rollout 回退为 token_count 毫秒时间戳 + 本次用量（`t:<ms>:<input>:<cache_read>:<output>`）；组内按键取并集，每键保留总量最大的那份副本的观测（同一 `response_id` 取值不一致时取大）。只要有键来自首份（size 最大）以外的副本或取值不一致，即计 `conflict_session_groups`（语义收窄为真实分叉）并经 `LOCAL_SOURCE_NOTICE` 说明「会话副本已分叉, 已按单次响应合并」；短副本是长副本前缀时不算分叉、无说明。记录行按需字段反序列化（不建 JSON DOM），release 构建冷扫耗时与 C190 前持平。
- **Codex 用量口径与累计计数回退 (C191)**：每条 token_count 优先取 `last_token_usage`（本次响应用量）；`input_tokens` 含缓存读取与缓存写入（Codex 解析用例：input 100 = cached 40 + cache_write 60，total = input + output），故非缓存输入 = input − cached − `cache_write_input_tokens`，缓存写入单列为 `cache_creation`（不区分 TTL；价卡无 OpenAI 缓存写入价时按 1.0× 输入价计，C193）；缺失时（旧版 rollout）取 `total_token_usage` 相对文件内高水位的增量。累计值回退到文件内**出现过**的值是重放旧快照，记 0 且不动基线；回退到**从未出现过**的值视为计数重置（旧版恢复会话后从 0 重计），本条按当前累计值计入并以其为新基线——此前回退区间一直按 `saturating_sub` 记 0，直到超过旧高水位。回退次数记入 Codex 按文件缓存条目（`counter_resets`），有回退的会话数经 `LOCAL_SOURCE_NOTICE` 说明，命中缓存的轮次同样可见。实测本机 1,413 条 token_count 全部带 `last_token_usage`，现行 Codex 不走该路径。
- **usage 口径漂移哨兵 (C193)**：来源升级改了 usage 字段名或嵌套时，适配器会静默记 0 或丢行，用户只看到数字骤降。各引擎按缓存单元记录 `UsageProbe`——「应带用量的候选行数」与「末尾连续取不到非零用量的候选行数」：会话文件（JSONL 引擎的 Claude / CodeBuddy / Kimi / Pi、Codex rollout、dsh 会话）末尾连续 ≥ `FILE_DRIFT_STREAK = 5` 条、数据库（OpenCode message / ZCode model_usage，按 rowid 序）末尾连续 ≥ `DATABASE_DRIFT_STREAK = 20` 行即疑似口径变化，经 `LOCAL_SOURCE_NOTICE` 说明（不把 agent 置 error）。候选行由适配器界定（Claude `assistant`、CodeBuddy 助手消息 / function_call、Kimi `usage.record`、Pi 助手消息、Codex 带 `info` 的 token_count、dsh `assistant/message`、OpenCode 助手消息、ZCode 每行），字段缺失与取值全零同样计为取不到；Grok 按内容估算不参与。为防改名后的行在入口被滤掉：dsh 预筛加 `assistant/message`，OpenCode 查询加 `OR data LIKE '%"assistant"%'`。哨兵随缓存条目持久化（JSONL / dsh 载荷 `u`、Codex 条目 `usage_probe`、SQLite 条目 `usage_probe`），追加 / 增量读取按「追加段取到用量即清零、否则接续」合并，命中缓存的轮次说明不消失；旧条目缺省为空，不强制重建。阈值依据本机实测：Claude / Codex / dsh 全部会话末尾连续零值 0 条、任意位置最长 1 条，ZCode 4 万行中最长 5 行。ZCode 列改名仍由 schema 指纹拦截为故障。
- **超长疑似用量行 (C195)**：单行超过 `MAX_JSONL_RECORD_BYTES`（1 MiB）的记录只计 `truncated_lines` 后跳过；其中**保留前缀命中该来源结构化用量字面量**的行才是疑似用量行——JSONL 引擎用各适配器的预筛字面量（C110 的必要条件，均为带引号的结构化形式），Codex 用 `"token_count"`、dsh 用 `"usage"` / `"assistant/message"`（不用裸字面量：工具结果等字符串里的字面量落盘为 `\"…\"`，不会命中）。计数记入 `UsageProbe.truncated_usage`（随缓存条目持久化，追加段累加；Codex 同会话副本按组取最大），非零时经 `LOCAL_SOURCE_NOTICE` 说明「N 条疑似用量记录超过 1 MiB 单行上限, 已跳过未计入」，命中缓存的轮次同样可见；`ScanStats.truncated_lines` 只反映本轮重读的文件，不用于说明。本机 Claude 4 条超长行均为 `user` 工具结果 / 图片（前缀无结构化 `"assistant"`，真实助手行首个 `"assistant"` 最晚在第 170 字节），不产生说明。目录深度上限 `MAX_DIRECTORY_SCAN_DEPTH = 16` 只防 symlink 环（真实布局最深约 3 层），不属少计来源，不加说明。
- **单文件失败不中止整源、三套缓存同口径 (C196)**：JSONL 引擎（Claude / CodeBuddy / Kimi / Pi / Grok）中，文件在列目录与 `stat` / 读追加指纹之间被删除、截断或变为不可读（会话清理、日志轮转的竞态）时只跳过该文件、计 `io_errors`，其余文件照常聚合——此前 `fs::metadata(path)?` 与 `append_is_safe(..)?` 上抛，整个来源本轮按 `LOCAL_SOURCE_IO_DEGRADED` 跳过，`found=false` 时还被误标为 `history`「本机未发现会话来源」。追加指纹读取失败按「不可追加」走整文件重解析；解析失败（追加段或整文件）时，若该路径有同身份（schema / source / parser / aggregation / 时区一致）的旧条目，沿用其陈旧载荷继续本轮聚合，只计 `io_errors`（不计 `cache_hits` / `cache_rebuilds`），旧条目原样留在磁盘、签名仍不一致，下一轮重试；无旧条目时本轮不计入该文件。`stat` 失败的文件已登记进本轮 seen，缓存条目不回收；真被删除时下一轮按 manifest 差集回收。至此 dsh（C189）、Codex（C197）与 JSONL 三套缓存的失败口径一致：只缓存成功解析的结果、有旧条目即沿用。读取失败子目录下条目按差集回收的行为维持现状（台账已保护历史，条目可再生）。
- **Grok 时间戳与独立解析口径 (C194)**：Grok 会话行只有 `type` / `content`，用量按内容 chars/4 估算（note 写明「按消息内容估算 (不含每轮重发的上下文, 偏低)」——每条消息只计一次，不含每轮重发的上下文与系统提示，相对实际计费输入系统性偏低）。时间口径：来源带消息级时间（`timestamp` / `created_at` / `createdAt`，ISO 或秒 / 毫秒数值）时优先使用；没有时取解析该行时的文件 mtime，追加段的新观测取当时的 mtime，**已缓存的观测保留首次记录的时间**（走 JSONL 引擎默认 `merge_append`）。此前 Grok 覆写 `merge_append` 把已有观测整体重打为新 mtime，整段历史随最后一次写入漂移到新日期，叠加 T26 台账按日取大即成永久重复计数（实测 07-26 写入 300、07-27 追加 40 → 台账 07-26=300、07-27=340，7 日合计 640、月行 340）。限制：缓存条目重建（版本升级 / 损坏 / 文件被改写）时整文件按当前 mtime 重新归日，已追加过的会话会再次集中到最后写入日——台账单调合并会保留旧日期的值，需由 C199 的向下修正清除。Grok 声明独立的 `GROK_PARSER_VERSION`（v3），口径变化只重建 Grok 条目，不连带 Claude 等其他 JSONL 来源（它们仍为 `JSONL_CACHE_PARSER_VERSION = 2`）。
- **额度账号并发 (C122)**：额度查询由 `RuntimeLimits.account_tasks`（默认 4）个工作线程按计划顺序领取账号执行，工作线程数即账号并发上限；每次外部请求持一个网络许可（`network_workers`，默认 4，二者不同时网络许可才会节流）。每轮只执行一次账号计划，且计划键（app + account id）唯一 —— 目录账号来自 map 键、官方 provider 与多账号 service id 不同形、`codexQuotaAccountOrder` 重复即拒绝（`account_plans_have_unique_account_keys` 锁定），故不再叠加账号许可与 single-flight 去重；若将来引入同一轮多次执行或可重复的计划键，须先恢复去重再接入。
- **额度重试通用契约 (TD-005 / C138)**：`context.quotaRetryOnly = true` 表示「只重试额度，不扫描本机会话」；额度计划一律经 `build_account_plan`（覆盖全部 provider 与账号计划），产物固定为空 `agents` + 额度 `services`，不再存在按 codex 名字短路的独立入口。重试仍只装配被挑战账号的凭据；旧 `codexQuotaRetryOnly` 字段已从 Bridge 白名单、请求 schema 与双端调用方移除。
- **请求契约只保留被消费的字段 (C123)**：`collector-bridge` 白名单即请求契约 —— capabilities 仅 `localSessions`（本机会话统计，计价随之执行）与 `externalQuotas`；context 与 credentials 白名单中的每个字段都必须有 collector 内的消费方。已退役并被显式拒绝：`localPricing`、`subscriptionQuotaOnly`、`subscriptionProviders`（定向刷新的语义完全由「只授予 `externalQuotas` + 只装配目标 provider 凭证」表达）、`providerEnv`（从无写入方；Windows 旧凭据文件中的该字段读取时丢弃）。新增字段须与消费方同卡交付，并同步 `schemas/request-v1.schema.json`。C177 起 `timeouts.localScanSeconds` 同样退役 —— 本机扫描从来只受 `moduleSeconds` 整轮 deadline 约束，该字段只被校验、从未被读取；两端停发。为兼容升级替换与重启之间仍在运行的旧宿主，Bridge **接受但丢弃**该字段且不校验取值（与上列「显式拒绝」不同；schema 标 `deprecated`），timeouts 内其他未知字段照常拒绝（`retired_local_scan_seconds_is_accepted_but_not_validated` 锁定）。
- **宿主超时预算 (C177)**：mac 以子进程运行 Collector，请求 `moduleSeconds = 90`、`externalRequestSeconds = 10`，`CollectorRunner` 另有外层定时器在 Rust deadline 之外终止子进程；Windows 进程内执行，请求 `moduleSeconds = 150`、`externalRequestSeconds = 30`，只有 Rust deadline 一道约束。Windows 取值自 T02（2026-10-06）沿用，未记录取舍依据；两端差异暂不统一（统一需要两端真机的网络与扫描耗时数据），调整任一端须同步本条。
- **额度策略入口 (T14 / T16)**：入口 `collector_policy::handle_request` 收 `policy-request-v1` 字节、总是返回 `policy-response-v1` 信封。T14 曾以 `Bruce-collector policy` 子命令暴露给 mac；T16 起 mac 静态链接 `collector-policy-ffi`（C ABI `bruce_policy_call` / `bruce_policy_free`，JSON 字节进出，panic 不越过边界）进程内调用，子命令随之退役，`Bruce-collector` 仍只有采集 Bridge 一个入口。操作只有 `quotaPlan` / `quotaMerge` / `quotaAnnotate`（design/08），只做纯计算：不扫描、不出站、不读写文件。请求只含 artifact 的 `services` 与时间 / 间隔 / 意图等纯数据（不传整份 artifact），顶层与各操作字段按白名单拒绝未知字段（`POLICY_INVALID_REQUEST`），任意层级出现凭据形态的键（token / secret / password / apiKey / cookie / authorization / credential / oauth / `*QuotaAccounts`）一律以 `POLICY_CREDENTIAL_FIELD_REJECTED` 拒绝且不回显其值；解析失败、时间格式错误与已捕获的 panic 均以结构化诊断返回。
- **参照实现只在测试构建中存在 (C126)**：`collector-local` 的对外接口只有缓存扫描（`scan_*_cached` 与 `scan_codex_cached_with_cancellation`）；不走缓存的 `scan_claude` / `scan_codex` / `scan_kimi_tree` / `scan_grok` / `scan_pi` / `scan_codebuddy` / `scan_opencode` / `scan_zcode`（及 `*_with_cancellation`）、`scan_codex_cached`（不带取消令牌的包装）以及仅为它们服务的目录遍历与 SQLite 打开函数是对拍参照实现，以 `#[cfg(test)]` 只编进测试构建，缓存实现与参照实现的逐字段对拍不变。
- **缓存写盘口径 (C047 / C175)**：一切缓存写盘统一 `create_new + 0600 (unix) + 失败清理 + rename`，不留 umask 窗口；可再生缓存（JSONL / SQLite 条目、JSONL manifest、Codex 按文件缓存）**不强制落盘**（不 `sync_all`；macOS 上即 F_FULLFSYNC，曾占冷扫描约四分之三耗时）—— 掉电后可能留下空 / 截断条目，读取时按 Corrupt 计入 `cache_corruptions` 并全量重建，结果与无缓存解析一致（`jsonl_cache_entries_left_empty_or_truncated_are_rebuilt`、`sqlite_cache_entry_left_empty_or_truncated_is_rebuilt`、`codex_file_cache_left_empty_or_truncated_is_rebuilt` 锁定）；manifest 解析失败按「无上一版」处理，只影响该轮的删除回收。凭据、快照等不可再生数据不走缓存写盘原语，其落盘纪律不受此条影响；
- **缓存公共原语单一实现 (TD-004 / C134)**：JSONL 与 SQLite 两层共用的缓存原语收敛在 `collector-local::cache_util`（`CacheLoad<T>`、`load_json_cache`、`write_json_atomic`、`fingerprint_range`、`ends_with_newline`、`fingerprint_head_tail`）。任何指纹/追加安全/原子写盘语义修复只改这一处；各适配器只保留自身身份、schema 版本与载荷结构。Codex 的 best-effort 树缓存写入与 `CodexCacheLoad` 因错误/取消语义不同，暂不强制合并，但指纹算法必须复用 `fingerprint_head_tail`；
- **provider 专属语义边界 (C048)**：provider 的失败语义（`failureKind` / 失败文案）、新鲜度（`freshness`）、鉴权挑战（`credential_challenges`）及凭据轮换（`credential_updates`）统一由 `collector-provider` 的 `QuotaProvider::finalize_outcome` 产出的 `ProviderOutcome` 标准化输出；官方凭据缺失提示与嵌套 OAuth 解包规则统一在 `CATALOG_SPECS` 声明；账户计划专属参数校验归属 `collector-application::account`；编排层（`execution.rs`）与协议层（`collector-bridge`）**严禁按 provider 名字硬编码分支**；
- **provider 目录单一事实源 (C049)**：provider 的 prefix / app / 凭据字段统一定义在 `collector-provider` 目录表（由 `catalog_entries()` 投影），其他 crate 一律派生，**禁止复写字符串**；一致性由 `catalog_entries_are_complete_and_unique` 锁定；
- **截断文案不得硬编码上限 (C050)**：诊断文案必须引用 `MAX_SOURCE_ROWS` 等常量，防止上限调整后文案失真；
- **出站台账缓存（C038 引入，C039 回收）**：`LedgerCache` 端口曾是 Cline `/usages` 逐单台账的跨运行增量管线（端口在 `collector-runtime`、`FileLedgerCache` 在 `collector-local`）；C039 将 Cline 三窗口切换为服务端权威端点直读（design/02 规则 5）后，该管线失去唯一消费者并整体删除（git 历史保留 C038 实现，台账端点在 design/02 备案为回退路径）。**现行约定：provider 一律无状态**，quota 类数据优先直读服务端权威聚合端点，不为窗口建模引入跨运行本地状态。

## 7. 扩展设计 (Additional Technical Design)

### 7.1 缓存持久化
- **位置（单一事实源）**：缓存根恒由 `collector-local::default_cache_root` 解析，App 侧不透传 `cache_root`（Windows 壳注入的也是同一函数结果）——macOS / Linux 为 `~/Library/Application Support/Bruce/collector-cache-v1`（**不是** macOS 惯例的 `~/Library/Caches`），Windows 为 `%LOCALAPPDATA%\Bruce\collector-cache-v1`（`LOCALAPPDATA` 优先，空白值视为未设置并回退 `~/AppData/Local`），使机器本地缓存不落 roaming profile。
- **分层结构（按源类型分四层，C021 起源级缓存；C116 起 Kimi Code CLI 并入 JSONL 层；C189 新增 dsh 按文件缓存层）**：

| 缓存层 | 实现位置 | schema 常量 | 覆盖源 | 形态 |
|---|---|---|---|---|
| JSONL 源级 | `jsonl_cache.rs` | `JSONL_CACHE_SCHEMA_VERSION = 3` | kimi-code-cli、kimi-work、claude-code、codebuddy、grok、pi | 每文件一条 `JsonlCacheEntry`（身份 `schema_version` / `source_id` / `source_path_digest` / `parser_version` / `aggregation_version` / `timezone`，**不含 `today` 与窗口天数**；文件签名与 `safe_offset` · `head_length` · `prefix_tail_length` · `head_fingerprint` · `prefix_tail_fingerprint`；载荷为 C176 紧凑形状：文件级 `project`、按文件去重的 `models` 表与 `observations`（每条 `k` 32 位十六进制去重键 / `t` 毫秒时间戳 / `m` 模型表下标 / `i` `o` `r` `w` `h` 五类 token，零值与缺省不落盘），与窗口无关）+ 一份 `JsonlCacheManifest`（源内已见路径摘要集合） |
| SQLite 源级 | `sqlite_cache.rs` | `SQLITE_CACHE_SCHEMA_VERSION = 3` | opencode、zcode | 每库一条 `SqliteCacheEntry`（`schema_fingerprint` / `signature` / `cursor`(rowid · timestamp_millis) / 身份三元组 `window_days` · `timezone` · `today` / `append_safe` / `diagnostic` / `contribution`；T26 起不再有 `capped`，历史保留由 §7.3 台账负责） |

| dsh 按文件缓存（C189） | `sources/dsh.rs` | `DSH_CACHE_SCHEMA_VERSION = 1` | dsh（DeepSeek Harness） | 单文件 `dsh-sessions-v1.json`：身份 `schema_version` / `source_id` / `parser_version` / `aggregation_version`，`files` 以路径摘要为键、每个命中的会话文件一条（文件签名 `device` · `inode` · `size` · `modified_ns` + 与窗口无关的 `CachedFilePayload`：文件级 `project`、`models` 表与 `observations`）。zstd 帧边界与行不对应，**不参与字节偏移追加**：签名未变直接命中、变化即整文件重建；源内已消失的文件条目随写回移除 |

  字段全集与逐字段语义以对应实现文件为准；本节只声明层级与身份判定口径，不做逐字段镜像，以免文档先行腐化。
- **复用与版本迁移**：条目参与复用以身份全项相等为前置（各层 `cache_identity_matches`：JSONL 层比对 schema / `source_id` / 路径摘要 / parser / aggregation / `timezone`；SQLite 层仍含窗口 `days` · `timezone` · `today`；Codex 层比对 schema / `timezone` 与逐文件身份）；任一项失配即**忽略该条目并重新解析**（无损重算，不删除文件，计入 `cache_invalidations` 而非 `cache_corruptions`）。缓存文件删除只发生在源文件从源路径集合中消失时（按各自 manifest 差集清理，计入 `cache_deletions`）。版本常量升级即令旧条目全部失配：JSONL 层 v2（C116）去掉窗口身份与按窗口压缩的贡献，v1 条目重建一次。
- **SQLite 层保留窗口身份（C117 实测决策，T26 复核）**：ZCode 窗口内行数从 C117 时的约 2.7 万增至 T26 时约 4 万、全量读取约 60 ms/天，而改存与窗口无关的观测值需在每轮热刷新解析约 3 MB 并重聚合，热路径回退大于每日节省，故 SQLite 层继续以窗口为身份、条目保存紧凑贡献（`AGGREGATION_VERSION` 门禁不变）。T26 起历史保留由独立台账（§7.3）承担，故每日跨零点的全量重建只影响解析成本，不再导致历史丢失。
- **缓存条目与窗口无关（C116）**：JSONL 层条目只保存观测值（时间戳 + token 计数 + 模型 + 去重键；项目为文件级字段，C176），每次运行按当前窗口重新聚合；跨日（`today` 变化）与改动窗口长度均直接命中缓存。旧版 Kimi Code CLI 专用引擎遗留的 `<64 位十六进制>.json` / `manifest-<64 位十六进制>.json` 由 `remove_legacy_kimi_cache` 清理（其余层文件均带 `jsonl-` / `sqlite-` / `codex-tree-` 前缀，不受影响）。发布冒烟 `scripts/collector-release-smoke.sh` 依赖该格式：按 `jsonl-*.json` 与 `"source_id":"kimi-code-cli"` 定位条目，把 `parser_version` 降为旧值后要求下一轮「忽略并重建」（重新解析且 `cache_rebuilds` ≥ 1）；改动条目文件名、`source_id` 或字段名时必须同步该脚本（C129：C116 改格式后冒烟仍按旧 `sourceKind` / `parserVersion` 查找，`build-test-app.sh` 恒失败）。

- **JSONL 逐文件流式聚合与紧凑载荷 (C176)**：扫描按目录遍历顺序把每个文件的载荷并入适配器的聚合器（`JsonlAggregator`），并入后即丢弃，不再同时持有全部文件的观测。无去重的来源（Kimi / Grok / Pi）逐条记入贡献；Claude / CodeBuddy / dsh 的跨文件去重表须看完全部文件，只保留 128 位去重键 + 定长用量（模型 / 项目为驻留表下标），产出顺序与旧实现相同 —— 去重表按键序、其后为无 id 的观测（按遍历顺序）。去重键取原 SHA-256（域分隔 + 命名空间 + 原始 id）的前 128 位（大端），数值序与旧 64 位十六进制键的字典序一致，故模型 / 项目的首见顺序不变（`compact_dedupe_keys_and_streaming_keep_claude_aggregation_order` 对参照实现逐字节锁定）。项目名由文件路径推导、同一文件恒定，提升为文件级字段。读取侧字段全部可缺省、未知字段忽略，旧版本条目照常解析后按版本不匹配重建一次、不计为损坏；模型下标越界或去重键格式不符判 Corrupt。Codex 按文件缓存沿用原观测类型与格式，不随本层变化。

- **dsh zstd 会话源与整文件重建缓存 (C189)**：dsh 会话位于 `~/.dsh/sessions/<workspace-dir>/<session-id>/session.vN.jsonl.zstd`（`$DSH_HOME` 覆盖家目录），每次追加事件各写一个独立 zstd 帧，故以多帧串接读取器逐帧 `FrameDecoder::init` → `decode_blocks(All)` → `collect_to_writer`（复用同一个 `FrameDecoder`，合法 skippable frame 跳过、其余解码错误按数据损坏处理），解压后逐行受 `MAX_JSONL_RECORD_BYTES` 约束。**实现红线**：不得用 `StreamingDecoder::read` 的返回 0 当帧边界 —— 该读取为实现环形窗口在未到帧尾时也可能返回 0，据此切帧会静默丢掉该帧剩余内容（实测真实会话丢约 55% 字节，单测难以发现，须以真实压缩码流夹具 + 字节数/行数断言锁定）；单帧内容另设 8 MiB 护栏防病态大帧（C192 起在解码中强制执行，见下）。解码器取**纯 Rust 的 `ruzstd`**（精确锁版）：免去 `zstd-sys` 的 C 编译链，macOS Universal 2 与 Windows Tauri 交叉构建无需备 C 工具链、可离线构建；代价是冷扫解码较 C 版慢（实测 11 个会话约 45 MB 解压冷扫 ~1.9 s），热扫不触解码（~0.02 s）。**帧边界与行不对应，解压后字节偏移不能用于增量追加**，因此缓存以文件签名（`device` / `inode` / `size` / `modified_ns`）判定：签名一致只读观测、不解压不解析，签名变化整文件重建（`cache_rebuilds`）。用量只认 `assistant/message` 的 `data.usage`：`inputTokens` 是非缓存输入、`outputTokens`、`cacheReadTokens` → 缓存读取、`cacheWriteTokens` → 缓存创建（来源不区分 TTL，`cache_creation_1h = 0`），`totalTokens` 是派生值不重复计入；模型取 `data.message.source.model` 原样（`deepseek-flash`、`cline-pass/deepseek-v4.1-flash-1017` 由价卡归一化命中），项目取会话头 `cwd` 的末段（文件级）。fork / seed 会话会继承历史消息，跨文件按 message id 的 SHA-256 前 128 位去重（同键保留总量最大者，复用 `DedupedAggregator` 的 `LargestTotal` 规则）。**活写撕裂兜底**：dsh 会话在采集期间仍在追加，偶发撕读会让最后一帧不完整；此时若缓存中仍有该路径旧条目，则沿用其陈旧观测继续本轮聚合，只计 `io_errors`，不计 `cache_hits`（未复用「已确认未变化」的条目）、不计 `cache_rebuilds`（重建失败）、不计 `cache_deletions`（旧条目未丢弃），陈旧条目保留旧签名故下一轮仍重试重建、写完即被真实观测替换；单个会话文件**永久**损坏时表现为该会话数字停在最后一次成功值（不消失、不误报故障），这是刻意的「陈旧但稳定」取舍。无旧条目的损坏文件仍按 `io_errors` 跳过，不影响同源其它文件。
- **dsh 逐帧隔离 (C192)**：zstd 帧彼此独立，此前任一帧解码失败或超限即整文件按损坏跳过（无旧条目时整个会话本轮为 0，永久损坏的文件每轮整文件重解压后再失败），且 8 MiB 帧上限只在帧头声明内容长度时预检——实测 dsh 帧头一律不声明（7,087 帧全部 2 MiB 窗口、带校验和、≤ 4 块、最大压缩帧 61 KB），整帧先解码进内存才后检。现在先按帧头 / 块头（RFC 8878，不解码）切出一帧的压缩字节再单独解码：块内容解码失败或已解出字节超过 `DSH_MAX_FRAME_CONTENT_BYTES` 只跳过该帧（帧尾由块头确定，不影响其后的帧）；帧结构损坏（魔数 / 保留位 / 保留块类型 / 块长越界，帧尾未知）时按魔数重新同步；声明窗口超过上限的帧整帧流式丢弃不缓冲；逐块解码并随时取出，超限即中止，峰值内存约为上限 + 窗口 + 一块。末帧在文件末尾被截断（活写撕裂）时其前的帧照常计入、计一次 `io_errors`、不算坏帧；只有首帧不可解时整文件按损坏上报（多半根本不是 zstd 会话），此时沿用上条活写兜底。部分成功的解析结果照常缓存（条目记录 `damaged_frames`），签名不变直接命中；坏帧数经 `LOCAL_SOURCE_NOTICE` 说明「N 个 dsh 压缩帧损坏或超过 8 MiB 上限, 已跳过这些帧」（撕裂末帧不计入，避免活写会话的说明时有时无）。

### 7.2 IPC 错误与降级
- 遇到个别日志行损坏或 JSON 截断：递增 `ScanStats.malformed_lines` 并平滑跳过，绝不中断整次采集；
- 遇到权限不足或外部 SQLite 独占锁冲突：产出 `ScanStats.conflict_session_groups` 诊断，保障其他正常源完整出库。

### 7.3 用量历史聚合台账与全量读取（T26）
<!-- @topic: TokenUsage -->

**问题**：artifact 的用量完全来自「本轮扫描当前来源」，没有任何独立历史台账 —— 来源被删除/清空/卸载、JSONL 文件被清理、Codex 缓存被写成空、ZCode/OpenCode 触顶 3 万行，都会让该 agent 的历史整段消失；App 只读 artifact，用量为 0 即从「Agent 表现」过滤掉。

**目标**：collector 侧建立 Bruce 自有的**派生数值历史台账**（只存统计值与日期，不存消息正文、路径、凭据），artifact 从台账投影；来源消失后历史仍可见。App 侧不改数据来源，双端仍只读 artifact。

**位置与所有权**
- 台账路径由 collector 解析：macOS/Linux `home/Library/Application Support/Bruce/usage-history-v1.sqlite`，Windows `%LOCALAPPDATA%\Bruce\usage-history-v1.sqlite`；目录 `0700`、文件 `0600`（权限收紧为尽力而为，chmod 失败不阻断台账可用），开启 WAL 与 `busy_timeout`。
- 归 collector 独占写；App 不打开该库。`清理用量缓存` 只清 App 快照与元数据，**不含**台账；删除台账只能由未来显式的「清空用量历史」入口执行（本卡不提供）。
- 台账是**不可再生**资产（与可重建的 `collector-cache-v1` 不同），写入失败不得删除或截断既有数据。

**数据形态**（`user_version = 2`，C199 起；v1 → v2 只给 `agent_state` 加列，既有 agent 记基线版本 1；`bucket_json` 为带 `cache_creation_1h` / `rate_splits` 的 `TokenBucket` JSON，保证历史成本可按当前价表重算）
| 表 | 主键 | 内容 | 保留 |
|---|---|---|---|
| `agent_day` | agent_id · date | 日 TokenBucket | 永久 |
| `agent_day_model` | agent_id · date · model | 日×模型桶 + 展示序 | 永久 |
| `agent_month_model` | agent_id · month · model | 月×模型桶 + 展示序 | 永久 |
| `agent_today_model` | agent_id · date · model | 今日模型桶 + 展示序 | 仅今日 |
| `agent_hour` / `agent_hour_model` | agent_id · date · hour(·model) | 今日逐小时总量/模型桶 | 仅今日 |
| `agent_project` | agent_id · date · project | 今日工程聚合 | 仅今日 |
| `agent_state` | agent_id | last_scan_at / last_found_at / derivation_version（C199） | 永久 |

**写入时机**：仅全量本机扫描轮（`localSessions` 能力且非 `quotaRetryOnly`）；每轮单事务提交；只在扫描结果非空时写入，**不写占位 0 行**。

**合并语义（单调、只增不减）**
1. 逐日比较：新扫描该日 total ≥ 存量 total 才替换该日桶与其日×模型行；小于则保留存量并计 `history_kept_days`。
2. 扫描未出现的日期**保留**（来源修剪、会话文件删除、换根、部分扫描失败均不得抹掉历史）。
3. 月×模型：按新月总量比较后整月替换；今日模型/小时/工程桶随今日整体替换；昨日及更早的临时表行在每轮清理。
4. 写入前过滤空桶；`agent_state.last_found_at` 仅在来源 `found` 时更新。
5. **口径升版修正轮（C199，唯一的向下路径）**：来源在 `collector_local::source_derivation_version` 声明派生口径版本（只在修复**多计**的解析规则变更时升版；修复少计或只改分类不升——单调合并会自行向上纠正；现行 grok = 2（C194），其余为基线 1）。来源可见（`found`）且声明版本高于 `agent_state.derivation_version` 时为修正轮：本轮扫描窗口（`window.day_list`）内每一天以扫描值替换，扫描没有的日期删除，这些日期的日×模型行与今日临时表随之重写；起始日（`-01`）在窗口内的整月按扫描值替换，跨窗口起点的月份仍按规则 3 单调（窗口外的日子不在本轮扫描里）；窗口外日期不动。随后记录新版本（取大，降级运行旧版本不回退），之后的轮次恢复单调。来源不可见的轮次不修正、不推进版本，等来源重新出现。取舍：修正轮之前已被来源修剪 / 删除的窗口内日期会降到当前可见值；修正轮中瞬时读不到的文件造成的下降，会在后续轮次由单调合并补回。实测 Grok 跨日追加的旧台账 07-26=300、07-27=340（7 日合计 640）在升级后的首轮变为 07-27=340、合计 340、月 340。

**读取投影**：按请求窗口重建 `UsageContribution`（`by_day` / `models_by_month` / `models_today` / `projects_today` / `hours` / `models_by_day` / `hour_models_today`），交给既有 `UsageAccumulator` 计价；窗口仍为 182 天、逐日×模型明细仍为 `DETAIL_DAYS = 31`，artifact 契约不变。更长历史保留在库内，扩展「全部历史」视图另卡处理。

**来源消失语义**：扫描 `found=false` 但台账在窗口内有量 → `agent.status = "history"`，`note = "本机未发现会话来源，显示已保存的历史用量（最后同步 <last_found_at>）"`，用量照常进入 artifact；`found` 字段仍只表示来源探测结果。App 侧把 `history` 视为非故障（不生成 `.agentIssue` 诊断）并显示「历史」标签（Windows 用量卡 C198 起与 mac 同口径，此前以 `status != "ok"` 判定把 history 误报为故障）；既有 `ok` / `not_found` / `error` 语义不变。

**失败降级**：台账打开/迁移/读写失败时输出信息级诊断 `LOCAL_HISTORY_STORE_UNAVAILABLE`（不参与 envelope `Partial` 判定），该轮回退为「仅扫描贡献」的旧行为；`SQLITE_BUSY` 超时不得阻塞刷新。

**移除 30k 截断**：ZCode/OpenCode 全量与增量读取改为按 rowid（或时间）游标**流式逐行聚合**，不设 `LIMIT`、不持有全量行；内存 O(1)，逐行检查取消令牌。删除 `MAX_SOURCE_ROWS`、`SourceScan.capped` / `SqliteReadResult.capped` / 缓存 `capped` 字段与 `LOCAL_SOURCE_ROWS_CAPPED` 诊断码（SQLite 缓存 schema 升至 v3）。全量读取在 rowid 可用时 `append_safe = true`，增量缓存恢复。

**已知限制**：来源数据向下修正默认不会回退（单调合并的代价），仅在来源派生口径升版的修正轮内按窗口替换（见合并语义 5）；Grok 以文件 mtime 充当时间戳的漂移问题见规则「Grok 时间戳与独立解析口径 (C194)」（已落库的重复值由 C199 修正轮清除）；时区变更后本地日期键可能分叉（与缓存身份重建同源）；升级前已被修剪/删除的来源历史无法回补；>182 天视图不在本卡。

**验收要点**：① 删除/清空任一来源后 artifact 仍出该 agent 历史且 status=history；② ZCode 39,719 行全量计入、冷热对拍等价；③ 跨日全量重建不丢历史；④ 占位 agent 不产生 0 行；⑤ 清理 App 快照不删台账；⑥ mac/Windows artifact 消费一致（Windows golden 重生）。
