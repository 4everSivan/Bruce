## 1. 简介

macOS 端以 Swift 实现刷新策略与视图模型映射，Windows 端以 Rust 实现同一套规则（`apps/win/viewmodel` crate 与 `src-tauri` 的 `quota_policy` / `runtime_core`），两端靠共享 golden fixture 对拍约束一致。2026-10-25 架构审查与随后的修复卡显示：凡尚无共享 fixture 的规则，两端都已各自漂移。本草稿评估把这些规则收敛为一份 Rust 实现、由两端共同调用的方案。

**批准情况**：2026-10-26 维护者对第 4.3 节三个待决问题的答复为「accept one extra collector call / only quota checks and carry-over / linking Rust into the Mac app」，即接受第一期每轮多一次 collector 调用、第一期范围只含额度门禁与额度回填、接受第二期在 mac 链接 Rust。据此本文转为现行基线，执行拆解为 T13–T16（第 4.3 节）。

## 3. 规范

### 3.1 目标

1. 同一条业务规则只有一份实现，两端行为天然一致，规则改动只改一处。
2. 保持本地优先：不引入任何网络服务；不扩大凭据的进程边界（凭据仍只经现有 Bridge stdin 传入 collector）。
3. mac 维持 Universal 2（Apple Silicon + Intel）构建与 macOS 14 最低版本；Windows 维持现有进程内调用。

### 3.2 非目标

- 不改动 UI 渲染层（SwiftUI 视图、Windows WebView 前端），只收敛「数据 → 决策 / 视图模型」的纯函数部分。
- 不改动 artifact 契约与 Bridge 请求契约（除新增调用入口外）。
- 不追求一次性迁移全部规则。

## 4. 设计详情

### 4.1 架构与行为（可选方案）

| 方案 | 做法 | 收益 | 代价 / 风险 |
|---|---|---|---|
| A. 维持双实现 + fixture 先行 | 每条共享规则必须先有 `tests/fixtures/*-parity` 用例，两端各自实现 | 零构建改动；已证明有效（有 fixture 的规则未漂移） | 每次规则改动两端各改一次；规则覆盖靠纪律，新规则容易漏 fixture |
| B. mac 链接 Rust 静态库（C ABI，JSON 进出） | 把规则提为 Rust crate，编为 aarch64 + x86_64 静态库合并后由 SwiftPM 链接；接口只收发 JSON 字符串 | 单份实现、进程内调用、可用于高频的视图模型映射 | mac 构建链新增 Rust 交叉编译与合并静态库步骤；Swift ↔ C 内存与错误边界需要专门测试；App 体积增加（未实测）；SwiftPM 对预编译静态库的接入方式需验证 |
| C. collector 新增策略子命令 | 规则提为 Rust crate；Windows 进程内直接调用，mac 经现有 `Bruce-collector` 以 stdin/stdout JSON 调用（如 `policy` 子命令） | 不引入 FFI 与新构建产物；沿用已验证的 Bridge 进程边界 | 每次调用一次进程启动（实测中位约 5 ms），只适合每轮刷新一次的低频策略，不适合随 UI 状态频繁重算的视图模型 |

### 4.2 核心业务规则

<!-- @topic: SharedPolicyCore -->

1. **分两期**（2026-10-26 批准）：
   - 第一期（方案 C）：**只**把额度门禁（`QuotaRefreshPolicy.plan` / `quota_policy::plan`）与额度回填（`QuotaCarryOverMerger` / `carry_over_skipped` 及时间戳标注）收敛为 Rust crate；Codex 快照合并、窗口边界唤醒与退避不在第一期。Windows 进程内调用该 crate；mac 在已是 async 的刷新流水线中经 collector 子命令调用（每轮多一次进程调用，维护者已接受），并删除对应 Swift 实现。
   - 第二期（方案 B，已批准方向）：mac 构建链链接 Rust 静态库（Universal 2）。先以第一期的额度策略改为进程内调用验证构建链、体积与稳定性（T16）；第一期子命令随之保留或退役由 T16 实测后写回本节。视图模型映射（面板、工作台分析、菜单栏摘要、状态灯）的迁移范围在 T16 验收后另行评审。
2. **fixture 仍是裁判**：迁移期间两端实现并存时，以现有 `*-parity` fixture 判定；迁移完成后 fixture 改为对 Rust 实现的回归用例，不删除。
3. **接口只走 JSON**：输入为上一份 artifact、启用集合、时间与间隔等纯数据，输出为策略结果 JSON；不跨边界传递凭据（凭据装配仍在各端原位置）。
4. **新规则默认进共享 crate**：第一期落地后，属于每轮刷新策略的新增规则不得再在单端实现。

### 4.3 验证与实现情况

- **实现情况**：
  - **T13（已实现，待人工确认）**：共享 crate `core/collector/crates/collector-policy`（只依赖 serde / serde_json / chrono）承载 `plan`、`merge`（完整回填）、`merge_round`（单轮合并）、`annotate_services` / `annotate_provider`（定向刷新时间戳）与 provider / 限流 / 时间判定助手；锁屏抑制（`suppress_external_quotas`）与启用集合未知（mac 测试桩）两种入参一并收入。Windows `quota_policy` 与 `runtime_core` 的对应函数改为 re-export / 薄封装。新增 `tests/fixtures/quota-carry-over-parity/cases.json`（14 例）后实测迁移前分歧：Windows 4 例（输出顺序 2 例、旧 `empty` 快照资格、改写成功 service 已有 freshness）、mac 1 例（失败借用漏 `balance` / `currency`）；按 design/02 规则 12 定口径后 mac 补借两个字段，Windows 由共享实现取代。
  - **T14（已实现，待人工确认）**：`Bruce-collector policy` 子命令与 `schemas/policy-request-v1` / `policy-response-v1`；入口 `collector_policy::handle_request`（字节进、信封出，T16 的进程内调用复用同一入口）；请求只含 services 不含整份 artifact（本机真实快照整份 187,433 字节，services 3,101 字节）；白名单拒绝未知字段与凭据形态键，错误为结构化诊断；共享 fixture 经子命令与进程内入口逐字节一致。
- **已确认决策（2026-10-26）**：① 接受第一期每轮多一次 collector 进程调用；② 第一期范围只含额度门禁与额度回填；③ 接受第二期 mac 链接 Rust 静态库。
- **任务拆解（M8，批次 0.14.0，均为 pending）**：
  - **T13**：抽出共享额度策略 crate（门禁 + 回填），Windows 改为调用；先补额度回填的双端对拍 fixture，再迁移。
  - **T14**（依赖 T13）：collector 新增策略子命令与请求 / 响应 schema，不携带凭据。
  - **T15**（依赖 T14）：mac 刷新流水线改调策略子命令并删除 Swift 门禁与回填实现；子命令失败时的降级语义由本卡确定并写回本节。
  - **T16**（依赖 T15，第二期）：mac 构建链链接 Rust 静态库（Universal 2），额度策略改为进程内调用，实测体积与启动影响；子命令去留与视图模型迁移范围写回本节。
- 每张卡以 quota-policy-parity（及 T13 新增的回填 fixture）与全量验证为验收。
