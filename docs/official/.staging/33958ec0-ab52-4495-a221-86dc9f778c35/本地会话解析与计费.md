# 本地会话解析与计费

本地用量模块把不同 Agent 的 JSONL 或 SQLite 记录归一化为四类 Token，再生成趋势、模型、项目、小时分布和参考费用。不同来源具有不同的记录与去重规则，缓存也按来源类型分层，不能把所有适配器都当作从旧偏移继续读行。

## 1. 目标与职责

本模块只读外部记录，持有 Collector 自有派生缓存。调用方提供采集窗口、来源路径和价格覆盖；输出是可合并贡献，服务端额度不在本模块计算。


<a id="chapter-2"></a>
## 2. 对外契约

<a id="source-window"></a>
### 2.1 时间窗口与来源路径

每次请求共用一个采集窗口（`CollectionWindow`）。`context.timezone` 默认 `UTC`，接受 IANA 时区；`context.days` 默认 14，允许 1 至 366；`context.now` 省略时使用当前 UTC 时刻。窗口按请求时区的自然日划分，今日小时分布也使用同一时区。跨时区或调整天数后，缓存需要按新窗口重新判断身份。

JSONL 文件遍历会先按修改时间做粗筛，最终记录是否入桶由时间戳所在自然日判断。粗筛下界 `cutoff_ts` 是当前时刻减去 `days+1` 天，不能把它解释为最终统计区间的精确起点。

下表列出默认路径或解析入口。`context.paths` 中同名键的字符串覆盖默认结果；环境变量影响默认解析，不覆盖请求显式指定的路径。

| 来源 | `context.paths` 键 | 默认路径或候选规则 |
|---|---|---|
| Kimi Code CLI | `kimi_cli_sessions` | `home/.kimi-code/sessions` |
| Kimi Work | `daimon_kimi_sessions` | 依次查找 macOS 和 Windows 的 `kimi-desktop` Daimon、独立 runtime、平铺 sessions 候选目录，选择第一个存在的目录 |
| Claude Code | `claude_projects` | `CLAUDE_CONFIG_DIR/projects`，否则 `home/.claude/projects` |
| Codex | `codex_sessions` | `CODEX_HOME/sessions`，否则 `home/.codex/sessions` |
| Orca 内的 Codex | `orca_home`、`orca_codex_sessions`、`orca_codex_accounts` | macOS 默认 `home/Library/Application Support/orca` 下的 runtime 与各账号 `home/sessions`；并入 Codex 根集合 |
| Grok | `grok_home` | `GROK_HOME`，否则 `home/.grok`；扫描 `sessions` 与 `archived_sessions` |
| OpenCode | `opencode_db` | 优先 `XDG_DATA_HOME/opencode/opencode.db`；Windows 检查本地与 roaming 应用目录，最后回退 `home/.local/share/opencode/opencode.db` |
| Pi | `pi_sessions` | `home/.pi/agent/sessions` |
| ZCode | `zcode_db` | `home/.zcode/cli/db/db.sqlite` |
| CodeBuddy | `codebuddy_projects` | `home/.codebuddy/projects` |

Kimi Work 的 macOS 首选目录为 `Library/Application Support/kimi-desktop/daimon-share/daimon/runtime/kimi-code/home/sessions`。Windows 对应候选位于 `APPDATA/kimi-desktop`，环境变量缺失时回退到 `home/AppData/Roaming`。

## 3. 内部结构

<a id="contributions"></a>
### 3.1 派生贡献与聚合维度

来源替换先更新按来源索引的映射，再按稳定顺序归并，流程如下。

![Kimi派生贡献经有界队列按来源替换，流关闭后有序归并](../assets/km/source-contribution-flow.svg)

图：来源贡献替换。仅表示 Kimi 替换事件的消费路径，其它来源仍使用自己的适配与归并规则。

Kimi Code CLI 扫描器产生来源替换事件（`SourceDeltaChange`）：`source_id` 标识来源，`removed` 与 `added` 表示旧贡献移除和新贡献加入。事件通过容量 1024 的有界队列进入 `consume_source_changes()`。消费者先维护按来源 ID 索引的贡献映射，重复来源替换不会反复累计；队列关闭后按来源 ID 顺序归并，避免生产调度改变结果。

所有来源最终共用 `UsageContributionBuilder` 和 `UsageAccumulator`。每日桶覆盖窗口内的日期，缺数据日补 0；自然月与模型维度保留窗口内全部样本。今日模型按总量降序取前五个，项目按今日总量降序取前三个，相同总量保留原有顺序。`models` 由今日前五个模型生成，`modelMonths` 则保存窗口内各自然月的模型总量；两者不是相同范围。

依据：[`collector-application/src/aggregation.rs`](../../core/collector/crates/collector-application/src/aggregation.rs) 的 `consume_source_changes()`；[`collector-domain/src/lib.rs`](../../core/collector/crates/collector-domain/src/lib.rs) 的 `SourceDeltaChange`、`UsageContributionBuilder`；[`collector-aggregate/src/lib.rs`](../../core/collector/crates/collector-aggregate/src/lib.rs) 的 `merge_delta()`、`finalize_with_pricing()`。

## 4. 详细设计

<a id="normalization"></a>
### 4.1 记录归一化与去重

四类 Token 桶（`TokenBucket`）分别保存普通输入 `input`、输出 `output`、缓存读取 `cacheRead` 和缓存创建 `cacheCreation`，`total` 是四者之和。面向趋势和今日模型的展示输入使用 `display_input()`，把普通输入与两类缓存相加。因此 `today.input` 与 `daily[].input`、`todayModels[].input` 的语义不同，不能再给后两者叠加缓存。

| 来源 | 记录口径与去重规则 |
|---|---|
| Kimi Code CLI、Kimi Work | 接受 `type=usage.record`，映射 `inputOther`、`output`、`inputCacheRead`、`inputCacheCreation`；两者使用各自缓存入口 |
| Claude Code | 接受 `type=assistant` 的 `message.usage`。有 `message.id` 时按摘要去重，对同一消息四类计数分别取最大值；无 ID 的记录直接累计。项目来自父目录，子代理目录添加“·子代理”标记 |
| Codex | 从 `turn_context` 或当前记录更新模型；优先使用 `last_token_usage`，缺失时以 `total_token_usage` 高水位差值计算；识别重复快照，避免重复计入。普通输入减去缓存读取后入桶 |
| CodeBuddy | 接受 assistant `message` 和 `function_call` 的可解析用量，按项目与会话范围内的消息 ID 去重；同一 ID 选择总 Token 较大的完整快照，总量相同时选择较新记录 |
| Grok | 读取 user 与 assistant 内容，以 Unicode 字符数除以 4、最少 1 估算 Token，分别计作输入与输出；时间取文件修改时间。追加时已有观察记录也改用当前文件时间 |
| Pi | 接受 assistant `message.usage`，输出包含 `reasoning`，`cacheWrite` 映射缓存创建；项目来自父目录 |
| OpenCode | 从 `message.data` 解析 assistant `tokens`，输出加 `reasoning`，`tokens.cache.read/write` 分别映射缓存读取与创建 |
| ZCode | 联查 `model_usage` 和 `session`，普通输入为 `input_tokens` 减去缓存读取与创建，输出加 `reasoning_tokens`；负数或无效整数按 0 处理 |

Codex 会合并官方目录与 Orca 目录中的候选文件。`rollout-*.jsonl` 按文件名分组，其他 JSONL 按头尾指纹分组；组内优先选较大的文件，再比较较新的修改时间，最后按路径稳定选择。副本比较使用物理文件身份或“首 64 KiB、末 64 KiB、长度”的 SHA-256 指纹，并非全文件哈希；内容冲突时仍只选择一份并输出诊断。

Grok 的结果是内容长度估算，不能作为服务商精确计量。CodeBuddy、Claude 与 Codex 的去重规则也不相同；直接逐行相加会丢失这些来源各自的去重语义。

依据：[`collector-domain/src/lib.rs`](../../core/collector/crates/collector-domain/src/lib.rs) 的 `TokenBucket`；[`collector-local/src/lib.rs`](../../core/collector/crates/collector-local/src/lib.rs) 的 `scan_reader_with_cancellation()`；[`collector-local/src/sources.rs`](../../core/collector/crates/collector-local/src/sources.rs) 的 `KimiWorkJsonlAdapter`、`claude_observation()`、`aggregate_claude_payloads()`、`scan_selected_codex()`、`resolve_codex_files()`、`aggregate_codebuddy_payloads()`、`grok_observation()`、`pi_observation()`、`OpenCodeSqliteAdapter`、`ZCodeSqliteAdapter`。

<a id="pricing"></a>
### 4.2 模型匹配与参考费用

`PricingTable` 先查找用户覆盖，再结合内置基准价。模型名称匹配会转小写、去掉 `[...]` 标签和最后一个 `/` 之前的前缀，并支持前缀兼容匹配。覆盖项可只替换已知模型的部分价格；未知模型至少同时提供输入与输出单价，才形成有效规则。

费用按以下公式计算，价格单位为每百万 Token：

```text
费用 = (普通输入 × 输入价 + 输出 × 输出价
      + 缓存读取 × 缓存读取价 + 缓存创建 × 输入价) / 1,000,000
```

未提供缓存读取价时，使用输入价的 10%。缓存创建使用输入价。未知且无完整覆盖的模型不计价，对应 `costUsd` 为 `null`；今日费用只汇总命中价格规则的模型，无法代表所有未知模型的完整成本。Agent 今日费用或全局费用不大于 0 时也输出 `null`，所以 `null` 不能单独区分“零费用”与“无可用价格”。

`todayModels` 的前五名截断不影响 Agent 今日费用：费用在全部今日模型上求和，`totalCostUsd` 再汇总各 Agent 的可用今日费用。该数值是本地参考成本，不是订阅实付账单。价格覆盖虽接受 `USD`、`CNY`、`EUR`、`GBP` 元数据，`calculate_cost()` 没有汇率换算，输出字段仍名为 `costUsd`；配置非美元价格时，不能把结果解释为已换算美元。

原设计文档中的“未知模型回退通用单价”与三项费用公式没有覆盖当前实现：实际未知模型返回无价格，公式另含缓存创建项。维护计费逻辑时应同时检查匹配、四类 Token 和空值语义。

依据：[`collector-domain/src/pricing.rs`](../../core/collector/crates/collector-domain/src/pricing.rs) 的 `PricingTable::resolve()`、`normalize_model_name()`、`model_matches()`、`calculate_cost()`；[`collector-aggregate/src/lib.rs`](../../core/collector/crates/collector-aggregate/src/lib.rs) 的 `finalize_with_pricing()`；[`collector-application/src/lib.rs`](../../core/collector/crates/collector-application/src/lib.rs) 的 `total_cost`；[原采集引擎设计](../devel/design/01-数据采集与多模型计费引擎.md) 的费用规则。

## 5. 流程与状态

<a id="cache"></a>
### 5.1 缓存的四种形态

macOS 与 Linux 的缓存根为 `home/Library/Application Support/Bruce/collector-cache-v1`；Windows 使用 `LOCALAPPDATA/Bruce/collector-cache-v1`，空白或缺失的环境变量回退到 `home/AppData/Local/Bruce/collector-cache-v1`。缓存是派生数据，与外部来源隔离。

| 缓存层 | 覆盖来源 | 复用与变更路径 |
|---|---|---|
| Kimi Code CLI 专用缓存 | Kimi Code CLI | 每文件保存紧凑贡献、文件签名、安全偏移和头尾指纹；manifest 保存路径摘要集合 |
| JSONL 源级缓存 | Kimi Work、Claude Code、CodeBuddy、Grok、Pi | 每文件保存紧凑贡献与派生观察记录，再按适配器规则聚合；manifest 跟踪文件消失 |
| SQLite 源级缓存 | OpenCode、ZCode | 保存 schema 指纹、库与 WAL 签名、行游标、窗口身份及派生贡献 |
| Codex 整树缓存 | 合并后的 Codex 根集合 | 保存整树签名、窗口与聚合结果；签名未变时复用，变化时重新选择文件并扫描 |

Kimi 与 JSONL 文件缓存先比较 schema、解析与聚合版本、来源身份、窗口及文件签名。文件没有变化时直接复用。只有文件增长、物理身份一致、旧安全偏移等于旧文件大小、旧前缀头尾指纹一致时，才从旧偏移解析追加内容。文件末尾没有换行时，安全偏移记为 0，后续增长会重建，避免把未完成记录当作完整追加边界。源文件删除后，manifest 差集会移除对应缓存贡献和缓存文件，不会删除第三方源文件。

SQLite 的追加条件独立于 JSONL，具体判定如下。

![SQLite缓存按身份签名、可解码贡献和安全游标决定复用追加重建](../assets/km/sqlite-cache-decision.svg)

图：SQLite 缓存判定。增量 I/O 失败或不安全结果回退全量，运行时取消和超时直接上抛。

SQLite 通过 `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_URI` 打开外部数据库。未变更时复用贡献；增量读取要求窗口天数、时区、今日日期、schema 与来源身份匹配，旧贡献可解码，文件签名满足追加条件且有可用 `rowid` 游标。签名包括主库大小与修改时间、WAL 大小与修改时间、文件身份和 SQLite change counter；不满足条件则重建。增量查询失败或返回不可安全追加的结果，也回退全量读取。

OpenCode 与 ZCode 的单轮候选行上限为 30000。可用排序列存在时，全量读取保留最新候选；缺少 `rowid` 时禁用游标追加，其中 OpenCode 的兼容 SQL 没有时间排序，不能保证它选中的是最新 30000 条。触顶或兼容降级会设置 `capped` 并保留诊断，当前响应状态把 `LOCAL_SOURCE_ROWS_CAPPED` 作为信息级诊断处理。

Codex 命中整树缓存仍需遍历目录、读取元数据，非 rollout 文件还可能读取指纹；“命中缓存”不代表零文件系统 I/O。若树缓存贡献结构异常，当前路径记录损坏并按可用部分聚合，不承诺一定立即重扫整个树。

依据：[`collector-local/src/lib.rs`](../../core/collector/crates/collector-local/src/lib.rs) 的 `default_cache_root()`、`process_cached_file()`、`append_is_safe()`、`make_cache_entry()`、`reconcile_deleted_cache()`；[`jsonl_cache.rs`](../../core/collector/crates/collector-local/src/jsonl_cache.rs) 的 `JsonlCacheEntry`、`append_is_safe()`；[`sqlite_cache.rs`](../../core/collector/crates/collector-local/src/sqlite_cache.rs) 的 `scan_sqlite_cached()`、`cache_identity_matches()`、`append_signature_is_safe()`；[`sources.rs`](../../core/collector/crates/collector-local/src/sources.rs) 的 `scan_codex_cached_with_cancellation()` 和 SQLite 适配器。

### 5.2 缓存判定与费用场景

JSONL 缓存的分支如下。SQLite 还要求 schema、WAL 签名和 rowid 游标，Codex 使用整树缓存，不套用该文件追加路径。

![JSONL身份和签名决定复用、安全追加或从零重建](../assets/km/local-cache-decision.svg)

图：JSONL 文件缓存判定。缓存写入失败和扫描取消由上游错误处理负责，图表示完成读取后的选择。

按实现推演：同一窗口内文件签名不变且缓存可解码，复用旧贡献；文件由 1000 增至 1200 字节，旧 safe_offset=1000、物理身份及旧前缀指纹匹配，才从 1000 读取追加段并合并。若旧文件末尾没有换行，safe_offset 为 0，增长后也重建。切换时区或今日日期使身份不符，同样重建，不能把旧日索引平移到新窗口。

价格决议先组合覆盖与基准，再计算四类用量。

![命中基准时合并部分覆盖，未知模型必须提供完整输入输出覆盖](../assets/km/local-pricing-decision.svg)

图：模型参考价格决议。这里是 Rust Collector 规则；分析工作台的比例估算有独立边界。

示例输入价为 2、输出价为 8，普通输入 100、输出 20、缓存读取 50、缓存创建 10，未给缓存价，则费用为 `(100×2+20×8+50×0.2+10×2)/1000000=0.00039`。这是公式推演。未知模型仅覆盖输入价时没有价格，不能把结果写成 0 美元。

依据：[`jsonl_cache.rs`](../../core/collector/crates/collector-local/src/jsonl_cache.rs) 的 `process_file`、`append_is_safe`、`make_entry`；[`sqlite_cache.rs`](../../core/collector/crates/collector-local/src/sqlite_cache.rs) 的 `scan_sqlite_cached`；[`pricing.rs`](../../core/collector/crates/collector-domain/src/pricing.rs) 的 `resolve`、`calculate_cost`。

## 6. 异常与恢复

<a id="read-failure"></a>
### 6.1 读取失败与终止

目录遍历共享深度上限 16 和已访问 canonical 路径集合，阻止符号链接环。JSONL 单条记录上限为 1 MiB；超长、损坏或不符合来源格式的记录计入对应统计并跳过。权限、数据库 schema、缓存损坏与行数截断具有不同诊断语义，不能一概归为“未发现记录”。

扫描与发布前检查共享取消令牌；取消后整次本地采集返回 `LOCAL_SOURCE_CANCELLED`，不发布新的部分本地工件。普通读取故障可保留其他来源，但以诊断和条目状态表达缺失；封套状态见[采集引擎与本地用量设计](采集引擎与本地用量设计.md)。

依据：[`collector-local/src/lib.rs`](../../core/collector/crates/collector-local/src/lib.rs) 的 `MAX_DIRECTORY_SCAN_DEPTH`、`MAX_JSONL_RECORD_BYTES`、`scan_reader_with_cancellation()`；[`collector-local/src/sources.rs`](../../core/collector/crates/collector-local/src/sources.rs) 的目录遍历与来源适配器；[`collector-application/src/lib.rs`](../../core/collector/crates/collector-application/src/lib.rs) 的 `collect_secondary_source()` 与发布前取消检查。
