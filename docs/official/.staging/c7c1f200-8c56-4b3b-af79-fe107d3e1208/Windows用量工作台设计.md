# Windows 用量工作台设计

Windows 设置页从后台缓存的完整 `AgentUsageArtifact` 生成工作台快照。Rust `viewmodel::analytics` 负责按范围计算，前端负责呈现、交互与异步结果顺序；工作台不从看板的 14 天展示条目反推完整历史，也不凭固定单价补造费用。以下为源码契约，不代表 Windows 实机验收。

<a id="chapter-1"></a>
## 1. 目标

用户可在设置页选择时间范围，比较 Token、费用、缓存、模型与 Agent，并导出当前范围模型 CSV 或完整工件 JSON。工作台只分析缓存中已有数据；查询和显示分析快照不触发新的采集。数据模型与 macOS 的 `WorkbenchAnalytics` 按跨端测试约定对齐，但平台窗口、文件保存和图表呈现分别实现。

<a id="chapter-2"></a>
## 2. 设计

<a id="windows-ranges"></a>
### 2.1 时间范围与 KPI

前端初始选择 `7d`，也可选 `today`、`30d`、`month` 和 `all`。点击按钮调用 `get_usage_analytics`，后端解析范围并读取当前缓存工件；范围非法返回 `UNKNOWN_RANGE`。缺工件或 `usageEnabled` 关闭时返回空分析快照。

分析器先排序所有 Agent 的 daily 日期并集，以最后日期为今日；并集为空时使用 `generatedAt` 日期。近 7/30 天取最后相应数量的日期，本月匹配年月，全部历史使用当前工件已有日期。今日 Token 取 today 桶，其余范围累加选中 daily。daily 的 input 包含缓存读写，计算原始输入时扣除两种缓存并将结果钳制为非负。

四格 KPI 为总 Token、费用、缓存收益和所选范围内有用量的活跃 Agent。费用与缓存收益按明细中已有金额累计；缺字段时显示不可用，不按固定单价估算。选中范围无明细桶与旧工件缺明细字段有所区别：前者可得到零，后者不可用于推断真实金额。缓存拆分缺失时，相应指标不可用。

<a id="windows-timeline"></a>
### 2.2 曲线与维度按钮

今日趋势有 24 个小时点，近 7/30 天与本月按日，全部历史按月。Agent、模型、Token 构成与费用按钮选择不同系列，折线和面积按钮改变绘制方式，鼠标可选择点并显示对应数据。模型系列仅取范围内前五个规范模型；费用累计全部明细中的可用费用，缺失费用在该曲线桶中按零参与累加，因此曲线不保证费用完整。

小时总量来自 `hours`，小时模型和构成依赖 `hourModels`；历史总量来自 daily，模型和费用依赖对应日或月明细。旧工件缺少必要拆分时不生成构成系列。峰值为第一个严格大于先前最大值的点，全零没有峰值；均值使用总量的整数平均。

<a id="windows-models"></a>
### 2.3 模型合并与渠道

分析器根据原模型名生成规范键，按键汇总选中范围的明细；来源以原始模型名及 Agent 区分。模型按 Token 降序、规范键升序排列，来源按 Token 降序、原名与 Agent 次序排列。汇总份额的分母是所有模型明细 Token，来源份额的分母是当前模型 Token。缺明细时不会按 daily 总量和历史份额虚构模型明细。

前端提供合并视图和原始渠道视图，并保存展开集合。CSV 是当前分析快照中的模型行，包含名称、厂商、Token、费用、份额和来源数；未定价模型的费用列留空。

<a id="windows-matrix"></a>
### 2.4 Agent 矩阵与 Token 构成

当前工作树的 Agent 和模型行调用品牌徽章模块，以身份图形区分来源，并保留图表系列色；若模块不可用，设置页回退原来的色点。资源与脚本仍为未提交状态，图标实际加载效果尚未验证。

矩阵只展示所选范围总量大于 0 的 Agent，按总量降序排列，并在有明细时展开模型与项目。项目仅在今日范围沿用采集端的 `projects`，历史范围不冒用今日项目。构成卡读取实际输入、输出、缓存读取和缓存写入指标；不能因为旧工件缺字段就将占位解释为零。24 小时密度条始终汇总今日小时值。

<a id="chapter-3"></a>
## 3. 流程

<a id="windows-lineage"></a>
### 3.1 分析数据来源

![Windows 工作台从缓存工件生成范围分析快照并供界面与导出消费](../assets/km/windows-workbench-lineage.svg)

图：工作台分析从缓存工件派生，不重新读取会话日志。

`get_usage_analytics` 从 `SchedulerControl` 取得缓存 artifact，传给 Rust 纯分析器，输出 KPI、规范模型、趋势、Agent 和今日小时统计。今日和历史总量来自工件的汇总桶，模型和费用来自相应明细桶；分析不写回工件。`settings-workbench.js` 请求快照后绘制卡片，切换范围时发起新的缓存计算，而非读取新日志。

<a id="windows-refresh"></a>
### 3.2 缓存更新与重新检查

每次分析请求递增 `seq`；若在结果返回前又发起较新的请求，旧结果被丢弃，避免旧范围覆盖新范围。后台发布更新后，设置页可以重新读取工作台快照。

来源区的“重新检查”调用 `refresh_now`，再读取运行信息及缓存面板。该命令只向容量为 1 的手动通道尝试提交请求，不等待采集完成；随后读取可能早于后台采集结束，提示文字也不是采集成功凭据。后台完成后通过事件发布新面板。采集失败时应结合运行阶段和诊断判断旧缓存是否保留。

<a id="chapter-4"></a>
## 4. 数据与接口

| 接口 | 输入与效果 |
|---|---|
| `get_usage_analytics` | 接收五种范围之一；读取缓存工件与用量开关，返回分析快照 |
| `export_workbench_csv` | 重新计算当前范围，导出规范模型行；无模型明细时报错，文件前置 UTF-8 BOM |
| `export_workbench_json` | 导出缓存中的完整 artifact；无工件时报错 |
| `refresh_now` | 提交手动刷新意图，不等待后台结果 |
| `dashboard-updated` | 后台发布面板变化，供界面更新 |

JSON 包含完整缓存工件中的用量与项目等内容；它不是仅包含汇总数据的诊断报告。CSV 的未定价空值也不能被解读为零费用。

<a id="chapter-5"></a>
## 5. 异常与边界

工件缺失或关闭用量时返回空快照；范围未知、导出缺数据及写文件失败经命令返回错误。一次异步请求被更新请求取代时，旧结果丢弃。旧工件缺少模型、费用或缓存细分时，对应展示可能为空或不可用；有价明细与无价明细混合时，已计费用只覆盖前者。全部历史仅是当前工件已有历史。

<a id="chapter-6"></a>
## 6. 验证要点

按源码推演，两个 Agent 的模型明细各为 100 和 200 Token 且规范键相同，合并行显示 300 并保留两个来源；其中一条未定价时，其费用不会作为零价写入 CSV。选中 30 天时，从工件 daily 日期并集取最后 30 项，并不受看板展示条数限制。连续切换范围时，旧请求晚到也不能覆盖较新的结果。

`analytics_parity.rs` 与前端测试包含分析和交互契约；本次没有执行测试，也没有验证 Windows WebView2、字体、悬停和原生保存对话框。
