# 构建验证与发布

Bruce 以 macOS 原生应用和 Windows Tauri 应用交付本地采集能力。工程分别提供本地验证、测试版组包、Windows 安装包与 tag 触发的发布流程。这里描述仓库脚本和工作流声明，不代表某次 CI、签名、公证或设备安装已通过。

## 1. 目标与范围

验证流程检查共享 Rust 采集与策略、平台适配和界面契约；打包流程把桌面宿主及所需资源组合为平台产物。项目没有自有应用服务器：macOS 宿主通过子进程运行内置 Collector，Windows 在原生进程内调用共享采集代码；按已配置订阅访问 Provider 属于出站请求。Widget 依赖外部宿主供数，不自动成为原生应用数据通道。

## 2. 环境与约束

macOS 构建需要 Swift、Rust 和系统 SDK；Universal 2 要分别构建 arm64、x86_64，再组合 App 与 Collector。macOS 还要构建共享策略静态库，供 Swift 宿主通过 C ABI 在进程内调用。Windows 安装包由 Tauri 和 NSIS 构建。CI 使用 macOS 26 与 Windows runner；工作流配置不能证明当前用户机器具备相同工具或外部凭据。

仓库根 `VERSION` 是发布版本来源；发布说明从 `CHANGELOG.md` 提取。更新签名密钥由环境注入，不能由源码或卡片中声称已配置推断实际密钥状态。手工 Developer ID 签名、公证与测试版的 ad-hoc 包是不同流程。

## 3. 部署拓扑

macOS 应用包同时携带原生 App 和 `Bruce-collector` 可执行程序。宿主在刷新时启动 Collector 并通过管道交换请求与响应，策略静态库则链接到宿主进程内。Windows Tauri 宿主进程内调用共享采集与策略 crate，再向窗口提供快照和事件。这些是源码和构建清单声明的进程边界，并非对当前设备的进程观测。

## 4. 组件与配置

| 对象 | 作用 |
|---|---|
| `scripts/verify-local.sh` | 串联本地 Rust、Swift、夹具和 Harness 检查 |
| `scripts/build-policy-ffi.sh` | 为 macOS 构建共享策略静态库；标准验证和应用组包也调用相应构建步骤 |
| `scripts/build-test-app.sh` | 组装 macOS 测试版 App，可选择 Universal 2 与 DMG |
| `scripts/build-win-app.ps1` | Windows 本地构建与打包；缺更新密钥时可按脚本路径跳过更新签名 |
| `scripts/generate-update-manifest.mjs` | 根据版本、双端资产和签名生成软件更新清单 |
| `scripts/upload-win-release.ps1` | 将 Windows 与更新资产加入选定的发布草稿 |

组包输出、测试缓存和用户运行数据承担不同职责；具体脚本已有路径与项目治理对 `local/` 的要求可能存在差异，不能据此推断所有工具已收拢输出。不得把开发机已有目录视为其他设备的运行事实。

## 5. 部署与变更流程

### 5.1 本地验证

标准入口先检查工具并运行 Rust 检查，再构建共享策略静态库、Swift 应用和 Harness，执行本地集成与界面模型检查，以及品牌资产、价卡和治理账本检查。具体 Harness 与作用以脚本为准；某一轮的成功必须有该轮命令输出，不能从脚本存在推断。

Windows CI 还声明前端结构检查、PowerShell 脚本语法与打包行为检查、发布管线契约检查，以及 Rust 共享 workspace、视图模型和 Tauri 壳的测试与 lint。静态脚本解析和本地夹具不等同于在 Windows 上完成完整安装或真实系统交互。

### 5.2 tag 发布

工作流在版本 tag 上运行 macOS 验证和 Universal 2 组包；发布作业等待验证与组包后创建含 ZIP、DMG、校验和与发布说明的草稿。Windows 发布作业等待 Windows 验证及草稿作业，构建带 updater 签名的 NSIS 安装包，生成 Windows 校验和，并通过上传脚本将签名和更新清单加入选定草稿。

清单生成使用该发布对应的 macOS 资产和 Windows 安装包；macOS ZIP 与 Windows 安装包的更新签名均是更新清单契约的一部分。更新签名与 Windows 系统代码签名是不同机制：工作流中的可选 `signtool` 步骤仍处于禁用占位状态，不能将 updater minisign 签名描述为系统代码签名。

### 5.3 正式包与安装

独立正式包脚本处理其签名和公证前提；本地 Windows 测试包可采用与发布作业不同的签名条件。安装、运行和平台验收需要分别检查实际产物、签名状态与对应系统上的行为；构建或发布流程定义本身不提供这些观察。

## 6. 故障与恢复

缺少必要工具、目标架构、版本资料或更新签名会使相应步骤失败，失败步骤及输出应作为该次构建证据。工作流要求 Windows 发布作业具备 updater 私钥；脚本生成清单时要求有效资产与签名，不能把未完成的草稿认作完整可用发布。重试前应核对实际草稿、资产和外部环境，避免仅根据历史卡片判断状态。当前内容不提供对某次失败作业或恢复操作的运行记录。
