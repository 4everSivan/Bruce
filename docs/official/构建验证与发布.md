# 构建验证与发布

Bruce 的验证、Preview 打包和正式签名打包是不同入口。当前 tag CI 使用 Preview 脚本组装 macOS 包，并在 Windows 资产补齐后发布 Release；Developer ID 签名与公证脚本保留为手工入口。

## 2. 环境与约束

macOS 组包依赖 Swift、Rust、系统 SDK 与 lipo；Universal 2 需要分别构建 App 与 Collector 的 arm64、x86_64，再各自合并。CI 声明 macos-26 与 windows-latest runner。手工正式包还要求匹配 HEAD 的 SemVer tag、正式 Bundle ID、Developer ID 及公证配置；环境变量中的凭据由操作者注入。

依据：[CI](../../.github/workflows/ci.yml)；[运行清单](../../scripts/runtime-manifest.zsh)；[正式打包脚本](../../scripts/build-release-app.sh)。

<a id="chapter-4"></a>
## 4. 组件与配置

VERSION 是跨平台版本来源；产物、应用资源、用户数据与知识文档分别管理。发布目录与构建中间目录沿用现有脚本，不能把规范要求的 local/ 收拢描述成所有工具已经实施。

| 对象 | 路径或契约 |
|---|---|
| macOS 组包 | dist/Bruce.app、dist/Bruce.zip |
| App 内采集器 | Contents/Resources/Bruce-collector |
| Windows 本地交付 | local/dist 下安装包或裸可执行文件 |
| 版本与说明 | VERSION、CHANGELOG.md、release-notes.sh |
| 用户运行数据 | 各端数据根与快照，见平台设计 |

<a id="bundle"></a>
### 4.1 macOS Preview 与产物组成

`zsh scripts/build-test-app.sh [--install] [--universal]` 构建 Rust Collector 和 Swift App，再组装 `dist/Bruce.app` 与 `dist/Bruce.zip`。`--universal` 分别构建并合并 `arm64`、`x86_64`；App 主程序与内置 Collector 各自必须包含所需架构。`--install` 另将包复制到 `/Applications/Bruce.app` 并注册 LaunchServices。

运行清单负责复制同一来源的 Collector、检查可执行权限，并拒绝在包内混入会话、数据库、fixture、Debug 目录或疑似凭据。`VERSION` 提供 Preview 应用版本。这里的 `dist/` 是项目保留且已忽略的输出例外；既有 Cargo 与 Swift 中间产物仍按脚本的 `target/`、`.build/` 路径生成。脚本中没有统一重定向这些中间产物到 `local/` 的实现。

依据：[`scripts/build-test-app.sh`](../../scripts/build-test-app.sh) 的参数解析与组包步骤；[`scripts/runtime-manifest.zsh`](../../scripts/runtime-manifest.zsh) 的 `Bruce_build_rust_collector()`、`Bruce_validate_release_bundle()`；[版本文件](../../VERSION)；[忽略规则](../../.gitignore)。

依据：[CI](../../.github/workflows/ci.yml)；[运行清单](../../scripts/runtime-manifest.zsh)；[正式打包脚本](../../scripts/build-release-app.sh)。


<a id="chapter-5"></a>
## 5. 部署与变更流程



<a id="verify-entry"></a>
### 5.1 验证入口与覆盖边界

`zsh scripts/verify-local.sh` 先准备 SDK 和 Cargo 环境，再执行 Rust 验证、Swift 构建和 Harness。`verify-rust.sh` 覆盖 Collector、Windows 视图模型与 Tauri 壳的格式、测试、Clippy，并执行 fixture 扫描；缺少 Node 时会警告并跳过 Windows 前端检查。macOS 后续步骤包括快照、Runner、刷新调度、生命周期、诊断、隔离集成、凭据、热键、缓存、玻璃材质、订阅刷新、品牌图形与 Panel 双端对拍等 Harness。

验证脚本最后的成功提示只在此前命令均退出成功时出现；提示本身不补足被条件跳过的检查，也不代表 Windows 桌面交互验收。Harness 数量随 `Package.swift` 与脚本演进，执行时应以这两个入口为准。

依据：[`scripts/verify-local.sh`](../../scripts/verify-local.sh)；[`scripts/verify-rust.sh`](../../scripts/verify-rust.sh)；[`apps/macos/Package.swift`](../../apps/macos/Package.swift)。

<a id="tag-publish"></a>
### 5.2 tag CI 的依赖与公开发布

工作流在主干 push、Pull Request 和 `v*` tag 上运行。macOS 验证与 Universal 2 组包并行；发布作业等待这两者后，用 Preview 包创建草稿，附 ZIP、SHA256 与从 CHANGELOG 提取的说明。Windows 验证单独执行，Windows 发布作业同时依赖 Windows 验证和 macOS 草稿作业。

Windows 发布采用固定版本 `tauri-cli 2.12.2` 构建 NSIS，随后 `upload-win-release.ps1` 分页查找同 tag 的最新 Release、清理同名旧资产并上传安装包和校验和，最后把 `draft` 改为 `false`、标记 latest。这是当前代码中的自动公开动作。签名步骤的 `if: false` 表示 Windows 签名尚未启用。

依据：[CI 工作流](../../.github/workflows/ci.yml) 的 `release`、`release-windows`；[`scripts/upload-win-release.ps1`](../../scripts/upload-win-release.ps1)；[`scripts/check-release-pipeline.mjs`](../../scripts/check-release-pipeline.mjs) 的流水线契约断言。

<a id="manual-package"></a>
### 5.3 手工正式包与 Windows 本地包

`zsh scripts/build-release-app.sh <tag>` 要求 `vX.Y.Z` 格式、tag 与当前 HEAD 对齐，并显式配置正式 Bundle ID、Developer ID 与公证所需环境变量。脚本包含 Hardened Runtime 签名、notarytool、stapler、Gatekeeper 检查和 Collector 安装升级回滚 smoke。它未接入当前 CI，不能将它的检查结果归给 CI Preview 包。发布说明入口 `release-notes.sh <version> [changelog-path]` 必须传版本参数；未找到对应 CHANGELOG 块时退出失败。

Windows 本地入口 `scripts/build-win-app.ps1 [-SkipInstaller]` 将最终安装包或裸可执行文件复制到 `local/dist`。Cargo 中间产物仍在 Tauri 的 `target` 下。脚本仅在未发现 `cargo-tauri` 时安装固定版本，不能据此保证本机已有 CLI 的版本。构建或安装前应结合原项目指南与已有 `local/deploy_report.md` 确认本机状态；知识库中的路径是程序契约，不是当前机器的部署实况。

原部署指南中的通用 `PORT=8080`、`npm run dev`、数据库和 `/health` 示例没有对应的 Bruce 服务入口。Bruce 的正常运行边界是本地桌面进程、文件快照和必要的 Provider 出站请求，不应套用这些模板参数启动一个服务。

依据：[`scripts/build-release-app.sh`](../../scripts/build-release-app.sh)；[`scripts/release-notes.sh`](../../scripts/release-notes.sh)；[`scripts/build-win-app.ps1`](../../scripts/build-win-app.ps1)；[原部署指南](../guide/01-本地部署指南.md)；[项目说明](../../README.md)。


<a id="chapter-6"></a>
## 6. 故障与恢复

本地命令任一受 set -e 约束的检查失败会中断后续步骤；条件跳过须另行判断。macOS 发布或 Windows 验证/打包/上传失败时，草稿可能已经存在，不能把 tag 创建当作双端交付完成。Windows 上传脚本处理同名资产替换，但发布链路不提供跨平台原子事务。

手工正式包脚本有安装升级与回滚 smoke；该入口未接入 tag CI，不能把它的签名、公证与 smoke 结论归给 Preview 产物。桌面进程没有 /health 或固定监听端口可供通用服务模板探活。

依据：[CI](../../.github/workflows/ci.yml)；[运行清单](../../scripts/runtime-manifest.zsh)；[正式打包脚本](../../scripts/build-release-app.sh)。
